    BACnet.Protocol.ObjectTypes.MultistateInput (bacstack v0.1.0-dev.2)

    View Source

    A Multistate Input reports one of several states, such as a valve's closed, midway or open position. State numbers start at 1. Use the optional state_text array to label them, with the first entry describing state 1.

    The number of valid states is declared by the required number_of_states property.

    Object Description (ASHRAE 135)

    The Multi-state Input object type defines a standardized object whose Present_Value represents the result of an algorithmic process within the BACnet Device in which the object resides.

    Multi-state Input objects that support intrinsic reporting shall apply the CHANGE_OF_STATE event algorithm.

    Samples and simulation

    The host's driver or local algorithm determines the input state in 1..Number_Of_States. Use set_input/2 to build an observation candidate. In service, a known sample updates Present_Value. While out of service, it preserves the simulated Present_Value. A selected Interface_Value follows the observation in either service state. :undefined marks the observation unknown and preserves Present_Value and Reliability. Sample validation applies even when Interface_Value is absent.

    BACnet Present_Value writes require Out_Of_Service, including same-value writes. property_writable?/2 reports that access policy. Explicit simulation from either origin can use update_property/3. Those writes leave Interface_Value alone. Returning to service preserves Present_Value until the driver supplies a fresh sample.

    Physical observations and Interface_Value

    The optional Interface_Value property describes the actual logical input state. Select it explicitly with a known state or :undefined at creation, or through add_property/3. A nil creation value omits it. An unknown observation encodes as BACnet NULL and a known one encodes as Unsigned.

    BACnet writes to Interface_Value are rejected. A local driver can report Interface_Value alone through the application-write lifecycle. Initialization preserves supplied property values. Observations do not select Interface_Value implicitly.

    State count and labels

    A local Number_Of_States edit resizes a selected State_Text array. Growth preserves existing labels and appends empty strings. A reduction truncates labels if Present_Value and any known Interface_Value still fit. If either would become invalid, the edit fails without changing the count or labels. Update the values first, then reduce the count. State_Text replacements must match the current count. The host needs to enforce the read-only service access for Number_Of_States.

    Lifecycle and host contract

    The object execution host needs to acquire samples, serialize operations and retain results per instance. Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 and an :initialization context. For a sample, construct a candidate with set_input/2 and an {:application_write, :present_value, nil, nil} context. Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 before committing the candidate, then execute with the same context and previous runtime state. Retain the complete result before exposing the write. Use :property_write for BACnet requests, including requests handled locally. The host needs to deliver each accepted write and enforce service permissions and array indices.

    Preparation checks the original and candidate service states for BACnet Present_Value writes. A rejected operation supplies no replacement result. Initialize before local operations. Missing, malformed or other-instance runtime state returns {:error, :invalid_execution_state}.

    Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 before reading with get_property/2. An active reporting delay can request a monotonic wakeup. The host needs to cancel any superseded request when retaining the result. The lifecycle consumes supplied observations and uses no polling timer, hardware callback or clock arithmetic.

    Reliability, restart and reporting

    The driver supplies Reliability from its diagnosis. A rejected sample or unknown input does not infer a fault. The host needs to suppress automatic Reliability reports while simulating. Either origin can supply explicit simulated Reliability. Inhibition masks physical reports with NO_FAULT_DETECTED and retains the latest report. An explicitly supplied or written out-of-service value can override the mask. Returning to service restores a known physical report, subject to inhibition. FAULT follows exposed Reliability, IN_ALARM follows supplied Event_State and OUT_OF_SERVICE follows Out_Of_Service. OVERRIDDEN is a local indication.

    After restart, initialize from restored properties with fresh runtime state. Refresh any suppressed physical Reliability report retained only in the old runtime state. Remote snapshots are passive and reject local write preparation and set_input/2.

    With intrinsic_reporting: true, CHANGE_OF_STATE compares Present_Value with Alarm_Values. FAULT_STATE uses Fault_Values when reliability evaluation is enabled. A reliability fault takes precedence over an alarm match. After retaining the result, the host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1.

    With Fault_Values configured, the algorithm supplies Reliability while evaluation is enabled. To retain an explicit out-of-service Reliability write, set Reliability_Evaluation_Inhibit to true before the write.

    The runnable walkthrough is examples/objects_lifecycle/multistate_input_lifecycle.exs.

    Examples

    Creating a minimal Multi-state Input:

    iex> {:ok, mi} = BACnet.Protocol.ObjectTypes.MultistateInput.create(1, "Mode", %{}); mi.present_value
1

    Selecting intrinsic reporting properties:

    iex> {:ok, mi} = BACnet.Protocol.ObjectTypes.MultistateInput.create(2, "Status", %{}, intrinsic_reporting: true); mi.object_name
"Status"

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
