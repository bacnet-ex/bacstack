    BACnet.Protocol.ObjectTypes.BinaryOutput (bacstack v0.1.0-dev.2)

    View Source

    A Binary Output commands a two-state actuator such as a relay or solenoid valve. The priority array selects the effective command in present_value. The driver can use get_output/2 to obtain the signal for the configured normal or reverse polarity.

    In addition to priority-based commandability and relinquish_default, the object provides optional min_off_time / min_on_time protection, logical transition history and elapsed active seconds. Actual feedback can be supplied separately through feedback_value. The existing auto_write_feedback option instead models feedback as following the logical command.

    Object Description (ASHRAE 135)

    The Binary Output object type defines a standardized object whose properties represent the externally visible characteristics of a binary output. A "binary output" is a physical device or hardware output that can be in only one of two distinct states.

    Binary Output objects that support intrinsic reporting shall apply the COMMAND_FAILURE event algorithm.

    Behaviour and Operation

    Binary Output objects are commandable two-state outputs. present_value is the logical command selected by the highest-priority non-NULL slot, or by relinquish_default when all commands have been relinquished. Use set_priority/3 to build command candidates - direct property updates of present_value are protected. Text properties describe the meaning of ACTIVE and INACTIVE. The related event state, reliability and out-of-service properties continue to supply the corresponding status flags.

    Logical commands and physical state are distinct. polarity translates the logical command at the hardware boundary: NORMAL preserves it and REVERSE inverts it. A polarity change can change the required physical signal without changing present_value. get_output/2 calculates that signal, with a caller-selected fallback while out of service. It neither operates hardware nor reports a measured state.

    Lifecycle and host contract

    The object execution host is the integrating application or higher-level BACnet stack that retains objects and runtime state, serializes operations and delivers requested wakeups. Initialize through BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 with :initialization and supplied clocks in BACnet.Protocol.ObjectExecution.Context. This module reads no clock, starts no process and invokes no hardware or property I/O callbacks.

    For each command, build a candidate, call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3, commit the returned candidate and execute with the same clocks and previous runtime state before exposing another operation. Retain the resulting object, state and replacement wakeup together. Use {:property_write, property, array_index, priority} for BACnet writes and {:application_write, property, array_index, priority} for local application updates. Deliver same-value writes too. Numeric property identifiers are accepted in triggers.

    Preparation reconciles priority holds and zero-write reset timestamps without I/O or runtime-state changes. Execution publishes transition history and active seconds. The host needs to service the returned monotonic wakeups and refresh computed reads through BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 before using the property getter. Raw property operations alone do not execute this lifecycle.

    Minimum on/off times and command priorities

    Priority 6 is reserved for the minimum-time mechanism. External set_priority/3 calls and lifecycle writes using priority 6 return {:error, :write_access_denied} even when minimum times are absent. An omitted command priority means 16. NULL (nil) relinquishes only its specified slot, and lower-priority commands are retained while masked.

    An effective logical transition starts min_on_time for ACTIVE or min_off_time for INACTIVE, in seconds. Priority 6 holds that new state until expiry. The expiry clears the hold and reevaluates commands. If that changes present_value, the new applicable hold starts. Priorities 1 through 5 can override a hold and restart timing for their new state. Same-value or masked writes do not restart timing. Duration edits reevaluate the hold from the last observed logical transition. Polarity does not affect this calculation.

    Logical transition history and active seconds

    change_of_state_time, change_of_state_count and time_of_state_count_reset form one optional group. Each effective present_value transition increments the count and stamps device-local wall time. Binary Output retains its existing non-negative integer count type without imposing a wrap limit. Physical feedback and polarity changes alone are not logical transitions.

    elapsed_active_time and time_of_active_time_reset form a second optional group. This implementation uses Present_Value as the active indicator, which is one of the alternatives permitted by ASHRAE 135-2016 12.7.17. It accumulates monotonic ACTIVE milliseconds into whole seconds and preserves the fractional remainder across inactive intervals. The unsigned 32-bit seconds total wraps modulo 2^32 without a reset stamp.

    A zero write to either total stamps its reset time, including same-value zero writes. Nonzero total writes are accepted and leave reset timestamps unchanged. Reset timestamps are writable. Writing an active-time total also clears its fractional remainder. Merely writing a reset timestamp does not clear a total. History and timing continue while out of service. Wall-clock corrections affect timestamps, not elapsed durations.

    Physical output, feedback and out of service

    The host needs to apply the retained logical command and polarity to its physical adapter while in service. It also needs to reapply the current command on return to service and when polarity changes. This module cannot confirm that the physical command succeeded. The host supplies actual feedback and physical reliability through property candidates and the same lifecycle write sequence.

    Out of service decouples physical drive and physical reliability. Logical application and BACnet commands, priority arbitration, minimum times and history continue. Physical adapter updates of feedback_value use an :application_write trigger and return {:error, :out_of_service} while decoupled. BACnet writes may simulate feedback. Explicit Reliability simulation is accepted from either origin, including same-value writes. The host needs to stop forwarding automatic hardware Reliability reports while out of service - origin alone does not identify the intent of a report. It also needs to isolate its hardware adapter and choose what the physical output does while decoupled. A get_output/2 fallback is a calculation input, not a universal safe-state requirement.

    feedback_value is available independently of intrinsic reporting. Without auto_write_feedback, command changes do not overwrite it. Supply actual feedback in the object's logical domain, after any hardware-specific mapping. This differs from the physical signal returned by get_output/2, especially with reverse polarity.

    With auto_write_feedback: true, existing property mechanics copy the logical command into feedback. This is command-following modeled feedback, including during out-of-service simulation - it is not evidence that hardware reached that state. Explicit feedback writes are rejected during lifecycle preparation with {:error, :feedback_managed_automatically} in this mode. Choose independent feedback when the adapter reports an actual state.

    Initialization, errors and capability boundaries

    Initialization establishes a baseline without inventing a transition, and preserves totals and reset timestamps. A stored priority-6 hold restarts its full applicable duration with the new monotonic origin. Obsolete holds are reconciled, counting any actual transition. Enable history groups at the operation where accounting should start - earlier history is not reconstructed. Reinitialize with fresh state after a VM restart.

    Invalid/cross-instance state or backwards monotonic time returns {:error, :invalid_execution_state}. Rejected writes leave the previous object, runtime state and wakeup unchanged. They do not change Reliability. Physical faults need explicit host-supplied reliability updates, subject to the out-of-service isolation above.

    With intrinsic_reporting: true, COMMAND_FAILURE compares the effective command with Feedback_Value. The event delay applies while they disagree and the normal delay applies once they match. The host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1 after retaining the result. Remote snapshots remain passive and request no wakeup.

    Commandability and Priority Arrays

    Binary Output always has priority_array and relinquish_default. Its effective logical command remains subject to prioritization while out of service. The priority array is read-only to BACnet clients - the host needs to enforce service access before preparing a write. The generated tables describe the remaining property relationships and encoding.

    Examples

    Creating a Binary Output with descriptive state texts:

    iex> {:ok, bo} = BACnet.Protocol.ObjectTypes.BinaryOutput.create(1, "Fan Cmd", %{active_text: "On", inactive_text: "Off"}); bo.active_text
"On"

    Selecting command-following feedback and the intrinsic property representation:

    iex> {:ok, bo} = BACnet.Protocol.ObjectTypes.BinaryOutput.create(2, "Pump", %{}, auto_write_feedback: true, intrinsic_reporting: true)
iex> {is_boolean(bo.feedback_value), bo.event_state}
{true, :normal}

    A complete lifecycle command with supplied clocks:

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> {:ok, object} = BACnet.Protocol.ObjectTypes.BinaryOutput.create(3, "Relay", %{min_on_time: 2, change_of_state_count: 0})
iex> start = Context.new(:initialization, now: ~U[2026-11-08 10:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, start)
iex> command = Context.new({:property_write, :present_value, nil, 8}, now: ~U[2026-11-08 10:00:01Z], monotonic_time: 1000, state: stored.state)
iex> {:ok, candidate} = BACnet.Protocol.ObjectTypes.BinaryOutput.set_priority(stored.object, 8, true)
iex> {:ok, prepared} = Lifecycle.prepare_write(stored.object, candidate, command)
iex> {:ok, stored} = Lifecycle.execute(prepared, command)
iex> {stored.object.present_value, stored.object.change_of_state_count, stored.next_execution.monotonic_time}
{true, 1, 3000}

    The runnable host-adapter walkthrough is examples/objects_lifecycle/binary_output_lifecycle.exs.

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.

    @spec get_output(t(), boolean()) :: boolean()

    Calculates the physical command from logical Present_Value and polarity.

    While out of service, returns decoupled_output_state unchanged, ignoring polarity. The default fallback is false.
