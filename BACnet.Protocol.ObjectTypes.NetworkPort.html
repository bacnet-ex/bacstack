    BACnet.Protocol.ObjectTypes.NetworkPort (bacstack v0.1.0-dev.2)

    View Source

    A Network Port exposes a device's communication settings and status through BACnet. A client can read the port configuration and request supported changes. The application connects those requests to its running transport.

    The Network Port object type defines a standardized object whose properties represent the externally visible characteristics of a network port of a BACnet device. All BACnet devices shall contain at least one Network Port object per configured port. It is a local matter whether or not Network Port objects exist for non-configured ports. It is a local matter whether or not the Network Port object is used for non-BACnet ports.

    Verification and validation of property values within a Network Port object is a local matter. Property values which are required to maintain proper operation of the network shall be retained across a device reset.

    Network Port objects may optionally support intrinsic reporting to facilitate the reporting of fault conditions. Network Port objects that support intrinsic reporting shall apply the NONE event algorithm.

    As specified in the standard (ASHRAE 135-2016, Clause 12.56), some properties of the Network Port object are required if the object is used to represent a network of a given type and protocol level. For example, a Network Port object whose Network_Type is MSTP must include the Max_Master property (when applicable), and a Network Port object whose Network_Type is IPV4 must include the BACnet_IP_Subnet_Mask property (when Protocol_Level is BACNET_APPLICATION).

    Aside from the properties so required, it is a local matter whether a Network Port object contains properties that do not apply to its Network_Type. Some vendors may find it convenient to have all of their Network Port objects support the same list of properties regardless of Network_Type. This is permitted, but not required.

    Object Description (ASHRAE 135-2016)

    The Network Port object provides access to the configuration and properties of network ports of a device. All BACnet devices shall contain one Network Port object per configured port. It is a local matter whether or not Network Port objects exist for non-configured ports. It is a local matter whether or not the Network Port object is used for non-BACnet ports.

    It is suggested that instances greater than 255 be used for Network Port objects with a Protocol_Level of PHYSICAL or PROTOCOL. When the Protocol_Level property has a value of BACNET_APPLICATION, the instance number (see Clause 20.2.14) shall correspond to the Port ID of the associated network as described in Clause 6.

    Behaviour and Operation

    Writes to configuration properties expose the proposed settings and set changes_pending. The first write to each property retains its previous value in the object metadata. The host can call active_configuration/1 for settings still in effect, such as the BDT used by the BVLL layer. The object and its pending metadata need to be persisted together when pending writes survive a reset.

    The object execution host handles BACnet.Protocol.Services.ReinitializeDevice. It needs to apply the pending configuration across affected ports as a single transaction for ACTIVATE_CHANGES or WARMSTART. After successful activation, execute each affected object with :periodic and network_port_event: {:configuration_activated, :activate_changes} or {:configuration_activated, :warmstart} in the context options. The host needs to serialize activation with configuration writes. RESTART_PORT is a command to reinitialize one port with its active settings.

    Commands

    Set supports_command_execution: true to select command with the initial value :idle. The object handles :discard_changes and accepts other commands through callbacks in the :network_port_runtime creation option. Each callback implements one action and receives the committed Network Port object. For a command write, the host needs to build a candidate with update_property/3 and call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3. On success it commits the candidate, acknowledges the BACnet write and then executes the committed object with the command write trigger. While the command is outstanding, another command write returns {:error, {:object, :busy}}.

    Execution restores :idle after the callback returns. For slave discovery, the callback should return once discovery has started. For restart, DHCP, foreign-device renewal, autonegotiation and proprietary commands, an error updates reliability and the fault flag. The execution result retains the callback outcome as a command_result/0. With intrinsic reporting selected, the command outcome is in the result state's execution_state field. DISCARD_CHANGES restores the active configuration while preserving live observations.

    Host responsibilities

    An :out_of_service runtime callback must disable or enable communication at the object's protocol_level. For an Out_Of_Service write, the host needs to prepare the candidate, execute the write on it and commit the successful result before acknowledging it. If the callback fails, the host needs to retain the original object. The callback must leave communication in its previous state on failure. If the write arrived on the affected port, the host and adapter need to allow the service response through.

    The host owns lower-layer port references, inherited settings, transport I/O, DHCP and foreign-device timers, and routing tables. It needs to validate the reference hierarchy and apply shared settings and referenced-port faults consistently across affected objects. It may enforce the optional single-client pending-change policy in Clause 12.56.13. Use update_operating_property/3 to record live transport values such as the negotiated link speed or DHCP addresses. The host supplies {:network_number_learned, number, configured?} as the :network_port_event when processing a Network-Number-Is message for an unconfigured port. See port_event/0 for the supported events. With intrinsic_reporting: true, reliability changes can generate FAULT and NORMAL transitions. The host retrieves the transition with BACnet.Protocol.ObjectExecution.EventReporting.transition/1 after retaining the result.

    The IPv6 UDP port uses the general pending-configuration mechanism in Clause 12.56.13. The ACTIVATE command mentioned in Clause 12.56.42 has no corresponding command value in Clause 12.56.14.

    Exposing IP addresses as read-only

    The host can expose a static IP address for discovery and diagnostics while restricting configuration to local administration. Use property_writable?/2 for the object's access rules, which make the IPv4 address read-only when DHCP is enabled and the IPv6 address read-only when automatic addressing is enabled. For a static address, add a host write policy that denies :ip_address and :ipv6_address for the selected Network Port instances.

    In BACnet.Protocol.Services.WriteProperty, resolve the object and property, then apply the policy before building a candidate. Return a BACnet error with class :property and code :write_access_denied for a denied write. Use the same policy for each write in BACnet.Protocol.Services.WritePropertyMultiple as it is processed in request order. Identify the denied object, property, and array index in the first failed write attempt of BACnet.Protocol.Services.Error.WritePropertyMultipleError.

    Reads still expose the configured address. If a local administrator or the operating system changes it, the host can record the new operating address with update_operating_property/3. To restrict client-triggered automatic address changes as well, apply the policy to writes to :ip_dhcp_enable and :ipv6_auto_addressing_enable and to commands that can restart address assignment, such as :renew_dhcp.

    This example applies the policy to every Network Port handled by the function. The same policy can use the port's object identifier to select individual ports.

    Example

    Stage a network number, then discard the pending change through the command property. The call to execute represents the step after the host commits and acknowledges the command write.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.NetworkPort
iex> {:ok, port} = NetworkPort.create(1, "Virtual port", %{
...>   network_type: :virtual,
...>   protocol_level: :bacnet_application,
...>   mac_address: <<1>>,
...>   network_number: 7,
...>   network_number_quality: :configured
...> }, supports_command_execution: true)
iex> {:ok, staged} = NetworkPort.update_property(port, :network_number, 8)
iex> staged.network_number
8
iex> {:ok, active} = NetworkPort.active_configuration(staged)
iex> active.network_number
7
iex> {:ok, candidate} = NetworkPort.update_property(staged, :command, :discard_changes)
iex> write = Context.new({:property_write, :command, nil, nil})
iex> {:ok, accepted} = Lifecycle.prepare_write(staged, candidate, write)
iex> accepted.command
:discard_changes
iex> {:ok, finished} = Lifecycle.execute(accepted, write)
iex> {finished.object.network_number, finished.object.changes_pending, finished.object.command}
{7, false, :idle}

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
