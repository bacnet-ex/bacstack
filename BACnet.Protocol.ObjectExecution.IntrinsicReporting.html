    BACnet.Protocol.ObjectExecution.IntrinsicReporting (bacstack v0.1.0-dev.2)

    View Source

    Evaluates an object's intrinsic event and fault conditions during lifecycle execution. Runs an object's intrinsic event and fault algorithms and records any transition.

    Using intrinsic reporting

    Create a supported local object with intrinsic_reporting: true and set its reporting properties. The object execution host runs the object through BACnet.Protocol.ObjectExecution.Lifecycle as usual. The object module selects the event algorithm and any fault algorithm.

    If you are implementing an object type, update its monitored values and any object-specific Reliability first. Then call evaluate/5 with that result, the current context, the event algorithm, the ordered property list for CHANGE_OF_RELIABILITY and any fault algorithm. For example, BACnet.Protocol.ObjectTypes.BinaryInput uses BACnet.Protocol.EventAlgorithms.ChangeOfState and [:present_value]. The evaluator returns the supplied result unchanged for a remote snapshot or when intrinsic reporting is off.

    BACnet.Protocol.ObjectTypes.EventEnrollment evaluates its configured algorithms through its own lifecycle. It shares transition bookkeeping and the result accessor in BACnet.Protocol.ObjectExecution.EventReporting.

    Detection, delays and retained state

    A Reliability fault takes precedence over an alarm. When the fault clears and the alarm condition still holds, the return to normal can request an immediate continuation to evaluate that alarm.

    Event_Algorithm_Inhibit suppresses alarm detection and clears an active offnormal state. Reliability reporting continues. With a configured inhibit reference, the evaluator reads it through BACnet.Protocol.ObjectExecution.Context.read_property/2 and keeps the last inhibit value if the read fails.

    Disabling Event_Detection_Enable resets the reporting properties and clears pending event delays. A configured fault algorithm still runs while Reliability_Evaluation_Inhibit is false. Event Enrollment uses its own detection policy and clears both algorithm states when detection is disabled.

    An alarm or recovery condition needs to hold for its configured delay. Delay deadlines use the context's monotonic milliseconds. The event timestamp uses the context's wall time when the transition is recorded. A reporting deadline can add a monotonic wakeup or bring an existing monotonic wakeup forward. Wall-clock deadlines and immediate continuations are preserved when adding a reporting deadline.

    Retain the complete BACnet.Protocol.ObjectExecution.Result for each object and pass its state to the next execution. This carries both the object's core state and the reporting state. After a VM restart, run :initialization with fresh runtime state and clocks. See BACnet.Protocol.ObjectExecution.Lifecycle for timer arming and delivery.

    Recording and delivering transitions

    When the evaluator detects a transition, BACnet.Protocol.ObjectExecution.EventReporting.record/5 updates the object's Event_State, alarm flag, timestamps, message text and acknowledgment bits. It uses the context's lookup_object callback to resolve the local BACnet.Protocol.ObjectTypes.NotificationClass and obtain the routing plan. Event_Enable controls the transition's enabled flag. A disabled transition or a missing routing plan still permits the object update.

    After committing each result, call BACnet.Protocol.ObjectExecution.EventReporting.transition/1 to get the transition, if any. If the transition is enabled and has a routing plan, the host needs to build and send the BACnet notification. Check the result before running an immediate continuation so transitions are handled in order. When handling AcknowledgeAlarm, commit the object returned by BACnet.Protocol.ObjectExecution.EventReporting.acknowledge/3. See the lifecycle delivery example.

    Buffer Ready

    For Event Log, Trend Log and Trend Log Multiple, the logger tracks the buffer and threshold. The log callbacks use evaluate_log/3 to check reporting against the current object, including a linked inhibit value, and request threshold evaluation from BACnet.Stack.TrendLogger.evaluate_buffer_ready/2.

    On a logger message with event: :intrinsic_reporting, the host finds the current object and retained state using the log identifier and executes with the :periodic trigger and the :trend_logger context option. The logger checks the current count during execution. A recorded TO_NORMAL transition advances Last_Notify_Record and resets Records_Since_Notification. Disabled detection, inhibition and an active reliability fault leave the threshold pending while collection continues. Event_Enable controls delivery of the recorded transition.

    Examples

    Alarm with a time delay

    Initialize an alarmed Binary Value with a two-second delay. The lookup resolves the Notification Class. Its default recipient list is empty in this example.

    iex> alias BACnet.Protocol.{DeviceObjectRef, EventTransitionBits, ObjectIdentifier}
iex> alias BACnet.Protocol.ObjectExecution.{Context, EventReporting, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.{BinaryValue, NotificationClass}
iex> enabled = EventTransitionBits.from_bitstring({true, false, false})
iex> {:ok, class} = NotificationClass.create(7, "Alarms", %{notification_class: 7, ack_required: enabled})
iex> {:ok, object} = BinaryValue.create(1, "Fan alarm", %{
...>   present_value: true, alarm_value: true, time_delay: 2,
...>   event_enable: enabled, notification_class: 7
...> }, intrinsic_reporting: true)
iex> lookup = fn %DeviceObjectRef{object_identifier: %ObjectIdentifier{type: :notification_class, instance: 7}} ->
...>   {:ok, class}
...> end
iex> initial = Context.new(:initialization, now: ~U[2026-11-11 10:00:00Z], monotonic_time: 100, lookup_object: lookup)
iex> {:ok, pending} = Lifecycle.execute(object, initial)
iex> {pending.next_execution.monotonic_time, EventReporting.transition(pending)}
{2100, nil}
iex> timer = Context.new(:timer, now: ~U[2026-11-11 10:00:02Z], monotonic_time: 2100, state: pending.state, lookup_object: lookup)
iex> {:ok, alarm} = Lifecycle.execute(pending.object, timer)
iex> transition = EventReporting.transition(alarm)
iex> {alarm.object.event_state, transition.enabled, transition.routing.ack_required}
{:offnormal, true, true}
iex> alarm.object.event_timestamps.to_offnormal == transition.timestamp
true

    Fault detection with FAULT_STATE

    Configure a BACnet.Protocol.ObjectTypes.MultistateInput with three states. State 1 is normal, state 2 is an alarm, and state 3 belongs to both the alarm and fault lists. The object applies BACnet.Protocol.FaultAlgorithms.FaultState to the sampled value. A sample of 3 sets Reliability to :multi_state_fault and records a CHANGE_OF_RELIABILITY transition to FAULT.

    When the input moves to state 2, reliability recovers and the object records a return to NORMAL. Since state 2 still qualifies for an alarm, the result requests an immediate continuation. The host commits and handles the recovery transition before running that continuation.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, EventReporting, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.MultistateInput
iex> {:ok, object} = MultistateInput.create(2, "Fan status", %{
...>   number_of_states: 3, present_value: 1, reliability: :no_fault_detected,
...>   alarm_values: [2, 3], fault_values: [3]
...> }, intrinsic_reporting: true)
iex> now = ~U[2026-11-11 10:00:00Z]
iex> initial = Context.new(:initialization, now: now, monotonic_time: 0)
iex> {:ok, normal} = Lifecycle.execute(object, initial)
iex> sample = fn stored, value, elapsed ->
...>   context = Context.new({:application_write, :present_value, nil, nil},
...>     now: DateTime.add(now, elapsed, :millisecond),
...>     monotonic_time: elapsed, state: stored.state)
...>   with {:ok, candidate} <- MultistateInput.set_input(stored.object, value),
...>        {:ok, prepared} <- Lifecycle.prepare_write(stored.object, candidate, context) do
...>     Lifecycle.execute(prepared, context)
...>   end
...> end
iex> {:ok, fault} = sample.(normal, 3, 100)
iex> transition = EventReporting.transition(fault)
iex> {fault.object.reliability, fault.object.status_flags.fault, transition.event_type, transition.to_state}
{:multi_state_fault, true, :change_of_reliability, :fault}
iex> {:ok, recovered} = sample.(fault, 2, 200)
iex> transition = EventReporting.transition(recovered)
iex> {recovered.object.reliability, transition.event_type, transition.to_state, recovered.next_execution}
{:no_fault_detected, :change_of_reliability, :normal, :immediate}
iex> continuation = Context.new(:continuation,
...>   now: DateTime.add(now, 200, :millisecond),
...>   monotonic_time: 200, state: recovered.state)
iex> {:ok, alarm} = Lifecycle.execute(recovered.object, continuation)
iex> transition = EventReporting.transition(alarm)
iex> {transition.event_type, transition.to_state}
{:change_of_state, :offnormal}

    An optional fault algorithm selected by the object module.

    A built-in module reads its inputs from the reconciled object:

    • BACnet.Protocol.FaultAlgorithms.FaultState and BACnet.Protocol.FaultAlgorithms.FaultCharacterString use Present_Value and Fault_Values.
    • BACnet.Protocol.FaultAlgorithms.FaultLifeSafety also uses Mode.
    • BACnet.Protocol.FaultAlgorithms.FaultStatusFlags uses Member_Status_Flags.

    For custom algorithms or other input sources, pass {module, constructor_args, updates}. The module's new/N returns its state struct, and execute/1 returns {:event, state, reliability} or {:no_event, state}. The state carries current_reliability. Nonempty keyword updates are passed to update/2 on subsequent executions. Use an empty list for fixed inputs.

    The two-element form {module, constructor_args} infers updates for [value, parameters] and [value, mode, parameters]. Other argument counts retain the state with fixed inputs. Vendor-specific BACnet.Protocol.FaultAlgorithms.FaultExtended requires a vendor implementation.

    evaluate(result, context, algorithm, fault_properties, fault_algorithm \\ nil)

    @spec evaluate(
  BACnet.Protocol.ObjectExecution.Result.t(object),
  BACnet.Protocol.ObjectExecution.Context.t(),
  algorithm(),
  [BACnet.Protocol.Constants.property_identifier()],
  fault_algorithm()
) :: BACnet.Protocol.ObjectExecution.Result.t(object)
when object: struct()

    Evaluates reporting after the object reconciles its properties and reliability.

    Supply the algorithm module selected by the object type. The evaluator converts the object's properties to the inputs required by that algorithm. Binary and multistate objects can share an algorithm module while supplying different BACnet value types. Use BACnet.Protocol.EventAlgorithms.None for reliability-only reporting.

    fault_properties lists properties in their required notification order. Unselected properties are omitted. Pass fault_algorithm to evaluate an additional fault condition. While reliability evaluation is enabled, the configured algorithm supplies Reliability and the FAULT flag on every execution, including recovery to :no_fault_detected. The evaluator retains the algorithm state between calls. When reliability evaluation is inhibited, the object supplies Reliability and the evaluator discards the fault algorithm state. Evaluation resumes with a fresh state built from the current inputs.

    Existing lifecycle wakeups are retained alongside reporting deadlines.
