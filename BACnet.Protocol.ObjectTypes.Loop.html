    BACnet.Protocol.ObjectTypes.Loop (bacstack v0.1.0-dev.2)

    View Source

    A Loop represents a feedback controller. For example, it can compare a room temperature with its setpoint and command a heating valve. The object exposes the measured value, setpoint, tuning and limits. Its present_value is the control output in output_units.

    Object Description (ASHRAE 135)

    The Loop object type defines a standardized object whose properties represent the externally visible characteristics of any form of feedback control loop.

    Behaviour and Operation

    Local objects use HvacPid.Controller by default. The implementation belongs to this module. The integrating application is the object execution host and needs to retain each result, deliver triggers and service replacement wakeups. BACnet.Protocol.ObjectExecution.Lifecycle documents that ordering and timer ownership.

    Initialize with BACnet.Protocol.ObjectExecution.Context containing fresh clocks, state: nil, and callbacks for the configured references. Initialization acquires one sample immediately when the controlled-variable reference is initialized. Each successful sample reads controlled_variable_reference and an optional setpoint_reference, publishes their values and computes present_value. Both inputs need to use controlled_variable_units. Reads accept native numbers or a primitive numeric BACnet.Protocol.ApplicationTags.Encoding, including a singleton encoding list. Values need to fit a finite BACnet REAL. Booleans and non-finite values are rejected.

    A computed result with a configured target requests :immediate. The host needs to retain the object and PID state before delivering a :continuation trigger. That continuation writes the captured output to manipulated_variable_reference at priority_for_writing. References are local BACnet.Protocol.ObjectPropertyRef values. The callbacks receive BACnet.Protocol.DeviceObjectPropertyRef values with a nil device and the configured array index. The host needs to validate and retain target writes. Callback exceptions and malformed responses remain programming errors.

    An object instance of 4194303 marks an uninitialized reference. An uninitialized controlled-variable reference lets the application supply readings directly. Without a referenced or application-supplied reading, the loop holds its output and requests no wakeup. Restoring the reference resumes control without integrating across the pause. An uninitialized manipulated-variable reference lets PID compute a local output without writing to another object. An uninitialized setpoint reference selects the fixed setpoint, as does %BACnet.Protocol.SetpointReference{ref: nil}.

    PID terms and units

    • proportional_constant is the shared gain in output units per controlled-variable unit. Its units property must be :no_units for this interpretation.
    • integral_constant is the reset time. Supported time units are :milliseconds, :hundredths_seconds, :seconds, :minutes and :hours. Reset rates in :per_second or :per_minute are converted to reset time.
    • derivative_constant is the derivative time in any of those time units.
    • An absent or zero constant disables its own term. With P disabled, the shared gain is 1.0 so I and D can still operate. Both signs of zero disable a term. Enabled constants must be positive. Other unit interpretations require an external controller.
    • action: :direct uses setpoint minus measurement, suitable for heating. :reverse uses measurement minus setpoint, suitable for cooling.
    • bias defaults to zero.
    • min_output and max_output bound the automatic output in output_units. Supply them in the properties map passed to create/4. On an existing Loop, use update_property/3 to change a bound that is present or add_property/3 to add an omitted bound. Each omitted bound independently uses the corresponding finite BACnet REAL limit, approximately -3.402823466e38 or +3.402823466e38. These are local control defaults. They do not describe the actuator's physical range.

    The controller's derivative source defaults to measurement. Set the creation option pid_derivative_on: :error to include setpoint changes. The first sample skips I and D. Configuration changes are applied at the next due sample with the bumpless transfer defined by HvacPid.Controller.configure/2. The controller also provides saturation anti-windup.

    Set the local pid_deadzone: creation option or call set_pid_deadzone/2 to configure a hold radius in controlled_variable_units. A positive radius holds the previous output and freezes the integral when the absolute error is at or below that radius. Zero is the default and disables the hold. Loop's BACnet deadband serves intrinsic event reporting (ASHRAE 135-2016, 12.17.33).

    Timing, overrides and restart

    update_interval sets the output cadence in milliseconds. An absent property selects a local default of 1000 ms. Built-in control requires a positive interval. With a referenced input, each due call takes one current sample and requests the next deadline one interval after the supplied monotonic time. Late calls do not replay missed samples. Early calls, including computed reads, preserve the current values and deadline. Changing the interval reschedules from the last attempt. Elapsed time between successful samples is converted to fractional seconds, so 1 ms is 0.001 seconds. Wall-clock changes do not move the monotonic schedule.

    The host can report an effective actuator output through context.options[:loop_effective_output] on a due execution. This reanchors the next output, for example after a higher-priority override or a pause. Supply it when a new transfer is needed. Supplying it on every sample reanchors every sample and prevents ordinary I and D progression. After a VM restart initialize again with fresh state and clocks. PID history and monotonic timestamps are runtime state, separate from the BACnet properties.

    Out of service and failures

    Setting out_of_service places an enabled controller in manual mode and stops sampling. The controller's manual command follows the finite present_value, including values outside the automatic output limits. With an initialized manipulated reference, a committed Present_Value write requests an immediate actuator continuation, including same-value writes. The host needs to deliver each committed write before the next operation. An uninitialized manipulated reference leaves the simulated write local.

    BACnet simulation can also publish and forward non-finite REAL values. The controller holds a finite manual command during that simulation. Returning to service restores the automatic limits and reanchors to a finite simulated output on a fresh sample. After a non-finite simulated output, automatic control starts with fresh PID history.

    Preflight rejects invalid control configuration or missing callbacks before I/O. Operational failures return a successful result with state.last_error retained for diagnostics. Failed acquisition leaves the published sample and output intact. A failed write retains the computed output and advanced PID state. It is attempted once for that continuation. The next scheduled sample can attempt a new command. Recovery reanchors from the retained output without integrating across the gap.

    When selected and evaluation is enabled, reliability becomes :configuration_error for invalid samples and reference/access failures, :communication_failure for other read/write failures, or :process_error for numeric controller failures. A successful automatic output write or local PID calculation clears that algorithm fault. Simulation and reliability_evaluation_inhibit preserve the selected Reliability value.

    Application-supplied readings

    Leave controlled_variable_reference uninitialized to supply the measurement from an application or device driver. Use update_property/3 to build a candidate with a finite controlled_variable_value in controlled_variable_units. Pass it through BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 with the trigger {:application_write, :controlled_variable_value, nil, nil}, then commit and execute the prepared candidate. The property is read-only over BACnet. Built-in control accepts these readings while in service.

    The application supplies each fresh reading, including repeated values. An early reading updates the published measurement and preserves the previous output. The first reading and subsequent readings at or after update_interval run PID. This mode requests no sampling wakeup. A referenced setpoint still requires the read callback. With a configured manipulated target, retain and deliver any immediate write continuation in the usual way.

iex> alias BACnet.Protocol.ObjectTypes.Loop
iex> {:ok, object} = Loop.create(1202, "Local sensor", %{setpoint: 21.0, proportional_constant: 2.0, proportional_constant_units: :no_units})
iex> context = Context.new(:initialization, now: ~U[2026-11-10 08:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, context)
iex> sample = %{context | trigger: {:application_write, :controlled_variable_value, nil, nil}, state: stored.state}
iex> {:ok, candidate} = Loop.update_property(stored.object, :controlled_variable_value, 19.0)

    External controller

    Set pid_enabled: false in create/4 to use the object as the BACnet representation of an application-owned controller. The option is retained in metadata. Execution preserves the object and supplied state and requests no wakeup or I/O. The application needs to own sampling, control, actuator writes and simulation propagation, and publish values through local updates. BACnet Present_Value writes still require out of service.

    iex> alias BACnet.Protocol.ObjectTypes.Loop
iex> {:ok, object} = Loop.create(1200, "External PID", %{}, pid_enabled: false)
iex> {:ok, object} = Loop.update_property(object, :controlled_variable_value, 20.0)
iex> {:ok, object} = Loop.update_property(object, :setpoint, 21.0)
iex> {:ok, object} = Loop.update_property(object, :present_value, 35.0)
iex> object.present_value
35.0

    Switching built-in control at runtime

    Use set_pid_enabled/3 to enable or disable built-in control on a local Loop. The option lives in object metadata, independently of out_of_service. Pass the retained runtime state and fresh clocks. Retain the returned result and apply its wakeup or continuation using the normal lifecycle ordering.

    Disabling publishes the stop command and stops sampling. With an initialized manipulated reference, provide a write callback and deliver the immediate continuation for the stop command. After the stop, the application can publish externally controlled values as described above. Enabling in service starts automatic control with fresh history. A Loop with an application-supplied input waits for its next reading. Enabling out of service selects manual mode using the simulated output.

    Set pid_start_value and pid_stop_value at creation, or use set_pid_start_value/2 and set_pid_stop_value/2 to update them for the next startup or stop. Values are in output_units and are clamped to the automatic limits. Without a start value the first valid sample uses bias plus the proportional term. Without a stop value the command uses min_output, or zero within the limits when min_output is absent.

    iex> alias BACnet.Protocol.ObjectExecution.Context
iex> alias BACnet.Protocol.ObjectTypes.Loop
iex> {:ok, object} = Loop.create(1203, "Runtime PID", %{present_value: 35.0})
iex> {:ok, object} = Loop.set_pid_stop_value(object, 10.0)
iex> context = Context.new(:periodic, now: ~U[2026-11-10 08:00:00Z], monotonic_time: 0)
iex> {:ok, disabled} = Loop.set_pid_enabled(object, false, context)
iex> {Loop.pid_enabled?(disabled.object), disabled.object.present_value, disabled.next_execution}
{false, 10.0, nil}
iex> {:ok, enabled} = Loop.set_pid_enabled(disabled.object, true, %{context | state: disabled.state})
iex> {Loop.pid_enabled?(enabled.object), enabled.object.out_of_service}
{true, false}

    Driving built-in control

    This finite example retains the result between the calculation and actuator write. Its write callback accepts the command. An application's callback needs to apply it and retain the target update.

    Intrinsic Reporting

    With intrinsic_reporting: true, execution evaluates FLOATING_LIMIT using Controlled_Variable_Value, Setpoint, Error_Limit and Deadband. Reporting also works when the host supplies the values and disables the built-in PID. After retaining the result, the host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1.

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.

    Sets the built-in PID's hold radius in controlled_variable_units.

    Supply a finite, nonnegative value. Zero disables the hold. The returned object applies the setting on the next automatic sample with its retained PID history. Startup and transfers establish the output before the hold takes effect.

    set_pid_enabled(object, enabled, context)

    @spec set_pid_enabled(t(), boolean(), BACnet.Protocol.ObjectExecution.Context.t()) ::
  {:ok, BACnet.Protocol.ObjectExecution.Result.t(t())} | {:error, term()}

    Switches built-in PID control for a local Loop and returns its lifecycle result.

    Supply the retained runtime state, fresh clocks and host callbacks in the context. Retain the returned result before delivering a continuation or scheduling a wakeup. A mode change with an immediate actuator write pending returns {:error, :busy}.

    Disabling publishes the controller's stop command, cancels sampling and queues an actuator write when a target is configured. Enabling in service starts the controller in automatic mode with fresh history. Enabling out of service selects manual mode with the simulated output. Reapplying the same setting preserves the current execution request.
