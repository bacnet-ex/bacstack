    BACnet.Protocol.ObjectTypes.EventLog (bacstack v0.1.0-dev.2)

    View Source

    An Event Log stores timestamped BACnet.Protocol.Services.ConfirmedEventNotification and BACnet.Protocol.Services.UnconfirmedEventNotification records. Use BACnet.Protocol.Services.ReadRange to retrieve the alarm and event history.

    Records contain the full event information (source object, event type, message text, priority, etc.). The log can be configured as a fixed-size circular buffer or a growing one (until stopped or full). It supports a time window (start_time / stop_time), enable/disable, and can itself generate a BUFFER_READY intrinsic event (when intrinsic_reporting: true) when the log has new data worth harvesting.

    Object Description (ASHRAE 135)

    An Event Log object records event notifications with timestamps and other pertinent data in an internal buffer for subsequent retrieval.

    Behaviour and Operation

    The host selects which sent or received notifications go to each Event Log. Submit selected notifications with BACnet.Stack.TrendLogger.trigger_log/3. The logger timestamps each record in its configured timezone and applies Enable, Start_Time and Stop_Time before collecting an event. The buffer overwrites its oldest records or stops logging according to Stop_When_Full.

    Lifecycle

    The object execution host needs to supply a running BACnet.Stack.TrendLogger.server/0 as :trend_logger in BACnet.Protocol.ObjectExecution.Context options. Execute with :initialization to register the local object. If that log is already registered, initialization reads its existing runtime state. Use the same logger throughout the lifetime of the object, and call BACnet.Stack.TrendLogger.remove_object/2 when removing the object.

    Execution reads Enable and the record counters together from the logger. Refresh before serving live properties and before preparing a write that depends on the buffer state. Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 and then execute each committed write, including repeated writes of the same value. A zero write to Record_Count purges the log and adds a buffer-purged status record. An Enable write that would start a full stop-when-full log returns {:error, :log_buffer_full}. The logger also checks this condition when applying the write. The host needs to return OBJECT/LOG_BUFFER_FULL at the service boundary and refresh the object if the logger rejected the commit.

    The logger owns the history and the time checks. The local object's log_buffer list stays empty during execution. To serve BACnet.Protocol.Services.ReadRange for Log_Buffer, use BACnet.Stack.TrendLogger.get_snapshot/2 and take the records and sequence information from that same snapshot. The object requests no wakeups. Remote snapshots execute passively.

    Intrinsic Reporting

    With intrinsic_reporting: true, the log's lifecycle evaluates BUFFER_READY against the current counters and reporting settings. Configure the notification_receiver described by BACnet.Stack.TrendLogger.start_link/1 and schedule a :periodic execution of the current log when the receiver gets an :intrinsic_reporting message. The execution consumes the threshold when it records a NORMAL transition for Log_Buffer. Collection continues during reporting inhibition, with the threshold pending for reevaluation. The host retrieves the transition after commit with BACnet.Protocol.ObjectExecution.EventReporting.transition/1.

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
