    BACnet.Protocol.ObjectTypes.Device (bacstack v0.1.0-dev.2)

    View Source

    A Device object identifies a BACnet device and exposes its capabilities and operating state. Its object identifier distinguishes the device from other devices on the BACnet internetwork.

    The object advertises protocol conformance (protocol_services_supported, protocol_object_types_supported, segmentation_support, etc.), vendor and model information, firmware version, and many operational parameters (max_apdu_length, apdu_timeout, database_revision, last_restart_reason, backup/restore status, active COV subscriptions, time synchronisation settings, object list, etc.). Several properties need special server-side handling.

    Object Description (ASHRAE 135)

    The Device object type defines a standardized object whose properties represent the externally visible characteristics of a BACnet Device. There shall be exactly one Device object in each BACnet Device. A Device object is referenced by its Object_Identifier property, which is not only unique to the BACnet Device that maintains this object but is also unique throughout the BACnet internetwork.

    Behaviour and Operation

    The Device object describes a BACnet device's identity, capabilities, object database, and operating state. Remote Device objects are snapshots, such as those returned by BACnet.Stack.ClientHelper.read_object/4.

    Lifecycle

    The object execution host supplies the device's current local time in the now field of BACnet.Protocol.ObjectExecution.Context.

    local_date, local_time, utc_offset and daylight_savings_status are sampled on demand. The offset uses standard time in minutes west of UTC. The daylight savings status reflects the separate daylight saving adjustment. For each requested property, the host can call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 with its :property_read trigger and use get_property/2 on the returned object. The host can reuse the same now sample when reading several clock properties together. Hosts that read without lifecycle execution can invoke the existing :on_read_function callbacks for local_date and local_time. Those callbacks sample the system clock using the stored utc_offset.

    To record a database change, restore or restart, the host needs to execute with :periodic and pass a device_event/0 as the :device_event context option. The host supplies each event once, after the corresponding operation succeeds. Database events and completed restores increment database_revision. Creating or deleting temporary configuration files during backup or restore leaves the revision unchanged. Ordinary property writes also leave it unchanged. A completed restore updates last_restore_time when selected.

    A completed restart updates last_restart_reason and time_of_device_restart when selected. With supports_restart: true, the recipient list defaults to a local broadcast. An empty list suppresses the notification. The host needs to supply the final system_status before calling restart_notification/1 on the updated object. It can then send the returned notification to the listed recipients. MS/TP slave devices cannot send this notification.

    Periodic time synchronization

    A positive time_synchronization_interval and at least one nonempty recipient list enable periodic synchronization. The interval is measured in minutes. With align_intervals enabled, intervals that divide an hour or a day align to local clock boundaries, shifted by interval_offset modulo the interval. Other intervals use elapsed time.

    The host needs to retain each execution result's state and use its wakeup for timer delivery. It needs to provide the device's timezone database and deliver :clock_change when changing the local clock or timezone. At each due :timer or :periodic execution, time_synchronization_requests/1 returns the requests prepared for that step. The host needs to send them once after committing that result. It resolves the recipient addresses and handles any delivery failures.

    Device-wide responsibilities

    The host owns the device clock, including initialization when no clock is available, and applies incoming BACnet.Protocol.Services.TimeSynchronization and BACnet.Protocol.Services.UtcTimeSynchronization requests to it. It also owns the object registry, address bindings and COV subscriptions. It needs to keep object_list, structured_object_list and active_cov_subscriptions current and commit database events with the corresponding registry changes.

    The host carries out reinitialization and the backup and restore procedures, including authentication and persistence. It also needs to apply changes to live settings such as APDU timeouts, retry counts and MS/TP parameters to the corresponding stack or transport components. For MS/TP, it needs to mirror max_master and max_info_frames from the enabled MS/TP Network Port with the lowest instance number.

    Slave proxy properties are available on local objects created with a revision below 19. A host supporting them needs to implement the proxy functionality.

    Examples

    Creating a basic local Device object.

    iex> {:ok, dev} = BACnet.Protocol.ObjectTypes.Device.create(123, "My BACnet Device", %{
...>   vendor_name: "Example Inc.",
...>   vendor_identifier: 999,
...>   model_name: "Demo Controller",
...>   segmentation_supported: :no_segmentation
...> })
iex> dev.object_name
"My BACnet Device"

    Sampling the clock before serving a read, then recording a committed object creation.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.Device
iex> {:ok, device} = Device.create(1, "Controller", %{
...>   vendor_identifier: 999,
...>   segmentation_supported: :no_segmentation
...> })
iex> now = ~U[2026-06-01 12:15:00Z]
iex> read = Context.new({:property_read, :local_time, nil}, now: now)
iex> {:ok, refreshed} = Lifecycle.prepare_read(device, read)
iex> {:ok, time} = Device.get_property(refreshed.object, :local_time)
iex> time.hour
12
iex> created = Context.new(:periodic,
...>   now: now, state: refreshed.state,
...>   options: [device_event: {:database_change, :object_created}]
...> )
iex> {:ok, changed} = Lifecycle.execute(refreshed.object, created)
iex> changed.object.database_revision == device.database_revision + 1
true

    Recording a completed restart when notifications are disabled.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.Device
iex> {:ok, device} = Device.create(1, "Controller", %{
...>   vendor_identifier: 999,
...>   restart_notification_recipients: [],
...>   segmentation_supported: :no_segmentation
...> }, supports_restart: true)
iex> restart = Context.new(:periodic,
...>   now: ~U[2026-06-01 12:15:00Z],
...>   options: [device_event: {:restart_completed, :warmstart}]
...> )
iex> {:ok, restarted} = Lifecycle.execute(device, restart)
iex> Device.get_property(restarted.object, :last_restart_reason)
{:ok, :warmstart}
iex> Device.restart_notification(restarted.object)
{:ok, nil}

    Driving periodic synchronization from a monotonic deadline. The second context represents timer delivery after the host has committed the initialization result. See BACnet.Protocol.ObjectExecution.Lifecycle for timer management examples.

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.

    Represents a Device object. Treat struct fields as read-only. Use the object module's property functions to build updates.
