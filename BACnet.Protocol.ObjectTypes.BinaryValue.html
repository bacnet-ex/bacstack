    BACnet.Protocol.ObjectTypes.BinaryValue (bacstack v0.1.0-dev.2)

    View Source

    A Binary Value holds an application flag such as an enable command, an alarm latch or a calculated Boolean result. BACnet clients can read and, where permitted, write its logical state. The object can also track transitions, active time and minimum on/off durations.

    The value is optionally fully commandable via a priority array (with relinquish default) so that schedules, operators, and control logic can arbitrate control. Its core lifecycle maintains optional transition history, elapsed active time and minimum on/off protection and intrinsic CHANGE_OF_STATE evaluation.

    Object Description (ASHRAE 135)

    The Binary Value object type defines a standardized object whose properties represent the externally visible characteristics of a binary value. A "binary value" is a control system parameter residing in the memory of the BACnet Device.

    Binary Value objects that support intrinsic reporting shall apply the CHANGE_OF_STATE event algorithm.

    Behaviour and Operation

    Binary Value objects are in-memory two-state parameters (mode flags, enable bits, calculated booleans, etc.). A non-commandable instance accepts present_value updates through update_property/3. When priority_array and relinquish_default are present, use set_priority/3 - the existing priority mechanism computes present_value. Text properties describe the intended meaning of the two states. Status flags continue to follow the related event state, reliability and out-of-service properties.

    Lifecycle and host contract

    The object execution host is the integrating application or higher-level stack that retains objects and runtime state, serializes operations and delivers triggers and requested wakeups. This object starts no process, reads no clock and performs no host I/O.

    Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2, supplying :initialization and fresh clocks in BACnet.Protocol.ObjectExecution.Context. Keep the returned object, state and wakeup together. Initialization establishes a baseline without inventing a transition or changing reset timestamps. A previously stored priority-6 hold starts its full applicable minimum duration again - elapsed time from another VM cannot be reconstructed. With no stored hold, initialization starts no minimum duration. Existing totals are retained, and any actual value change while reconciling an obsolete hold is recorded as a transition.

    For every write, build a candidate through the property API, call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3, commit the returned candidate and execute with the same context and previous runtime state before serving another operation. Use {:property_write, property, array_index, priority} for BACnet writes and {:application_write, property, array_index, priority} for local application writes. A local application present_value write is rejected with {:error, :out_of_service} while the object is out of service. BACnet writes, arbitration, timers and history accounting continue. Raw property setters have no source or clock information and do not perform this orchestration. Supply atomic write triggers even when the value is unchanged.

    Preparation computes priority holds and reset timestamps without changing runtime state or invoking I/O. Execution publishes transition history and active seconds and advances the retained runtime state before another operation may observe the object. Application writes use the same preparation and commit order as BACnet writes. Numeric property identifiers are accepted in triggers. Priority 6 is reserved for the module's minimum-time mechanism - set_priority/3 and lifecycle preparation reject commands using it. Direct client writes to the read-only priority array remain a host access check.

    Transition history and active time

    The optional change_of_state_time, change_of_state_count and time_of_state_count_reset form one property group. Every actual effective present_value transition increments the count and stamps device-local wall time. Same-value writes and commands masked by a higher priority do not count as transitions. A count of 4,294,967,295 wraps to zero on the next transition without stamping a reset.

    elapsed_active_time and time_of_active_time_reset form another optional group. Execution accumulates monotonic milliseconds spent ACTIVE, publishes whole seconds and retains the fractional remainder across inactive periods. Both groups operate while out of service. Zero writes to either total stamp its reset time, including repeated zero writes. Nonzero writes are accepted and leave the reset time unchanged. Reset timestamps are writable. Writing an active-time total replaces the total and clears its fractional remainder. The seconds total wraps modulo 2^32 without treating wraparound as a reset.

    Service the returned monotonic wakeups, and refresh computed properties through BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 before reading them. Wall-clock corrections affect timestamps, not elapsed durations. A backwards monotonic sample or runtime state belonging to another instance returns {:error, :invalid_execution_state}. Initialize again after a VM restart. Enabling a history group starts accounting at that operation's supplied time - it does not reconstruct history from before the group existed.

    Minimum on/off times

    min_on_time and min_off_time select optional minimum durations in seconds. For commandable instances, an effective transition places the new state in priority 6 for the applicable duration. Lower-priority commands are still stored. On expiry the hold is cleared, priorities are reevaluated and a new hold starts if the value changes. Priorities 1 through 5 may override a hold, and such transitions start a new hold too. Changing a minimum duration reevaluates the hold from the last observed transition.

    For non-commandable instances, the local mechanism rejects a conflicting value write with {:error, {:minimum_time_active, deadline}} until the monotonic deadline. It does not queue that rejected write or create a priority array. The caller may submit a new write when the duration expires. Same-value writes succeed without restarting a hold.

    Complete write example

    This example uses supplied clocks and retains each result in the caller. A running host additionally needs to service returned wakeups as described in BACnet.Protocol.ObjectExecution.Lifecycle. The runnable walkthrough examples/objects_lifecycle/binary_value_lifecycle.exs also covers command holds and resets.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> {:ok, object} = BACnet.Protocol.ObjectTypes.BinaryValue.create(22, "Enable", %{change_of_state_count: 0})
iex> start = Context.new(:initialization, now: ~U[2026-11-08 10:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, start)
iex> write = Context.new({:application_write, :present_value, nil, nil}, now: ~U[2026-11-08 10:00:01Z], monotonic_time: 1000, state: stored.state)
iex> {:ok, candidate} = BACnet.Protocol.ObjectTypes.BinaryValue.update_property(stored.object, :present_value, true)
iex> {:ok, prepared} = Lifecycle.prepare_write(stored.object, candidate, write)
iex> {:ok, stored} = Lifecycle.execute(prepared, write)
iex> {stored.object.present_value, stored.object.change_of_state_count, stored.next_execution}
{true, 1, nil}

    Capability boundaries

    With intrinsic_reporting: true, CHANGE_OF_STATE evaluates the effective value against Alarm_Value. The host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1 after retaining the result. Rejected writes leave Reliability unchanged. Remote snapshots remain passive and request no wakeup.

    Commandability and Priority Arrays

    Value objects can have a priority_array (making them commandable). When a priority array is present, the present value is protected and is only changed through the priority mechanism.

    Examples

    Creating a Binary Value with state texts:

    iex> {:ok, bv} = BACnet.Protocol.ObjectTypes.BinaryValue.create(20, "Mode", %{active_text: "Auto", inactive_text: "Manual"}); bv.active_text
"Auto"

    With the intrinsic reporting property group selected:

    iex> {:ok, bv} = BACnet.Protocol.ObjectTypes.BinaryValue.create(21, "Flag", %{}, intrinsic_reporting: true); bv.object_name
"Flag"

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.

    Represents a Binary Value object. Treat struct fields as read-only. Use the object module's property functions to build updates.

    Create the object with intrinsic_reporting: true to select its intrinsic reporting properties. The fields for those properties are nil when omitted.

    The present value reflects an in-memory logical state. No physical polarity is involved.

    For a commandable instance, use set_priority/3 to change the effective Present_Value.
