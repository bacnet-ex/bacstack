    BACnet.Stack.TrendLogger (bacstack v0.1.0-dev.2)

    View Source

    The Trend Logger module is responsible for handling event and trend logging and keeping a log buffer.

    Collects records for Event Log, Trend Log and Trend Log Multiple objects. Each registered log has its own buffer.

    For an Event Log, choose which events belong in the log and pass each one to trigger_log/3. For trend logs, the object's Logging_Type controls how samples arrive:

    • :triggered - Logging has to be manually triggered through BACnet. Call sample/2 to acquire the configured references or trigger_log/3 to submit data you already have.
    • :polled - The logger acquires the configured references on a timer.
    • :cov - The logger records matching change-of-value notifications for Trend Log objects.

    Forward local and remote COV notifications to notify/2. To have the logger manage remote subscriptions, supply a :cov_cb to start_link/1 and configure a positive Cov_Resubscription_Interval on the log. The callback needs to request confirmed notifications. The application handles routing incoming notifications, either through that adapter or through its own notification handler.

    Polled Trend Log and Trend Log Multiple objects support clock-aligned logging. Set align_intervals: true on the object, and specify log_interval and interval_offset in hundredths of a second. The alignment properties are optional and occur together - interval_offset defaults to zero when only align_intervals is supplied. Intervals that divide a second, minute, hour, or day align to that boundary in the configured timezone. The offset is reduced modulo the interval. For example, log_interval: 90_000 and interval_offset: 3_000 acquire at :00:30, :15:30, :30:30, and :45:30 each hour.

    Each completed acquisition schedules the next future aligned time, so lookup latency does not accumulate as clock drift. Missed periods are skipped - normal polling waits for lookup completion. Timers are realigned after detected system-clock or timezone offset changes. Acquisition and record delivery may be delayed by process scheduling or lookup latency. Polled records use the acquisition start time as their timestamp. COV and triggered logging ignore alignment. With alignment disabled, or an interval that divides none of the four units, polling uses a relative interval after each acquisition and ignores the offset. A zero interval in polled mode uses a relative one-second default.

    The logger sends messages to the optional :notification_receiver. Use add_object/3 to choose whether the logger evaluates BUFFER_READY itself or asks the application to run the object's lifecycle.

    Messages have the form {:bacnet_trend_logger, nil, object, metadata}. The object is the logger's snapshot of the registered log. An application that owns a lifecycle instance can use its identifier to find the latest object and retained state.

    • metadata.buffer holds the buffer module and a snapshot of the buffer.
    • metadata.event is :buffer_full or :intrinsic_reporting.
    • metadata.intrinsic_reporting contains a BACnet.Protocol.NotificationParameters.BufferReady payload for :intrinsic_reporting messages. In lifecycle mode, the payload signals that evaluation is due. Use the committed execution result for delivery.

    System clock changes are tracked using :erlang.monitor(:time_offset, :clock_service). Each nonzero offset change automatically adds a {:time_change, seconds} record to every enabled log within its logging time window, including event logs. The adjustment is signed and includes fractional seconds - records are timestamped using the current time after the change. Normal buffer limits and notifications apply.

    Detection follows the Erlang runtime's time warp mode and may be delayed. Multi time warp mode is recommended for detecting system clock adjustments. Timezone and daylight saving transitions are tracked separately by comparing the configured timezone's total UTC offset (utc_offset + std_offset) during the existing one-second logging time check. Each observed change adds a signed time_change record through the same logging path. Changes to timezone rules are detected when the configured timezone database starts returning a new offset. Detection can take longer when the logger is busy - only the net offset change between checks is recorded.

    Regional timezones require a configured Calendar.TimeZoneDatabase implementation - Elixir's default database only supports Etc/UTC. The timezone_database option can select a database for this logger. Restoring state starts tracking from the current system and timezone offsets - changes while the logger was stopped are not reconstructed.

    Functions

    add_object(server, object, mode \\ :standalone)

    @spec add_object(server(), object(), :standalone | :lifecycle) ::
  :ok | {:error, term()}

    Registers a BACnet.Protocol.ObjectTypes.EventLog, BACnet.Protocol.ObjectTypes.TrendLog or BACnet.Protocol.ObjectTypes.TrendLogMultiple with the logger.

    The third argument selects who drives BUFFER_READY evaluation. Record collection and buffering work the same way in both modes. The application handles any BACnet notification delivery in either mode.

    :standalone (default)

    Use this when your application manages the log directly through TrendLogger, for example to collect a local history. The logger uses the reporting settings of the registered object. Apply later setting changes with update_object/3. When the threshold is met and reporting is eligible, the logger advances Last_Notify_Record and resets Records_Since_Notification. An :intrinsic_reporting message carries the BUFFER_READY payload for that completed evaluation. The counters are available through get_snapshot/2.

    For example, given an enabled Event Log configured for intrinsic reporting, register it and submit an event notification to it directly:

    :ok = BACnet.Stack.TrendLogger.add_object(logger, event_log, :standalone)
:ok = BACnet.Stack.TrendLogger.trigger_log(logger, event_log, event_notification)
{:ok, snapshot} = BACnet.Stack.TrendLogger.get_snapshot(logger, event_log)

    Omitting the third argument also selects :standalone.

    :lifecycle

    Use this when a host, such as a BACnet device server, runs the log through BACnet.Protocol.ObjectExecution.Lifecycle. The log's initialization callback calls add_object/3 with :lifecycle automatically. Registering an existing log in this mode keeps its buffer and counters.

    With a configured notification receiver, :intrinsic_reporting requests an execution of the current log. The host uses the object identifier in the message to find the current object and its retained lifecycle state. Execution resolves the object's current reporting settings, including linked inhibition, and checks the latest record count. The counters advance when execution records BUFFER_READY. The host uses the transition from the execution result for notification delivery.

    For example, initialize a local log through its lifecycle, then run a periodic execution when the receiver reports :intrinsic_reporting for that log:

    alias BACnet.Protocol.ObjectExecution.{Context, EventReporting, Lifecycle}

options = [trend_logger: logger]
{:ok, initial} = Lifecycle.execute(log, Context.new(:initialization, options: options))

# Retain initial.object and initial.state. On a receiver message, use the latest pair.
context = Context.new(:periodic, options: options, state: initial.state)
{:ok, result} = Lifecycle.execute(initial.object, context)
transition = EventReporting.transition(result)

    Retain the complete result for subsequent executions, including any wakeup request. The transition is nil if reporting is inhibited or no transition is due. See BACnet.Protocol.ObjectExecution.IntrinsicReporting for the host flow.

    get_snapshot(server, object)

    @spec get_snapshot(server(), object()) ::
  {:ok, snapshot()} | {:error, :unknown_object}

    Returns a log's buffer, enable state and counters in a single read.

    Use the buffer module and buffer from this result together for BACnet.Stack.LogBufferBehaviour.read_range/3. For example, buffer_module.read_range(buffer, 0, 10) reads up to ten records from the start of the captured buffer. Later writes leave the returned snapshot intact.

    Notification counters reflect the logger's Buffer Ready processing. A transition resets records_since_notification and updates last_notify_record. A purge resets records_since_notification. The purge record can itself trigger a Buffer Ready transition.

    Returns {:error, :unknown_object} if the object is unregistered.

    sample(server, object)

    @spec sample(
  server(),
  BACnet.Protocol.ObjectTypes.TrendLog.t()
  | BACnet.Protocol.ObjectTypes.TrendLogMultiple.t()
) :: :ok | {:error, term()}

    Acquires one sample for a registered Trend Log or Trend Log Multiple in triggered mode.

    For Trend Log, the logger's lookup callback runs in the calling process and needs to bound its read time. Trend Log Multiple uses concurrent tasks with a one-minute timeout per lookup. Its record preserves the order of the reference array and holds a value or failure for each slot.

    Collection must be enabled at the start and end of the acquisition. Results from a previous registration, mode or reference are discarded.

    start_link(opts)

    @spec start_link(start_options()) :: GenServer.on_start()

    Starts and links the trend logger.

    Following options are available, in addition to GenServer.options/0:

    • :cov_cb - Optional callback for managing remote confirmed COV subscriptions. It receives the logger PID, a BACnet.Protocol.DeviceObjectPropertyRef, :sub or :unsub, the subscription lifetime in seconds and the requested COV increment (or nil). Return :ok or {:error, reason}. Keep the callback bounded. The logger waits for an in-flight operation before replacing a subscription and unsubscribes when the last enabled log stops using that remote reference. You can manage subscriptions separately and use notify/2 to forward notifications.

    • :log_buffer_module - Optional buffer implementation. It must implement BACnet.Stack.LogBufferBehaviour. The default is BACnet.Stack.LogBuffer. BACnet.Stack.LogBufferTree supports efficient range reads and ordered scans.

    • :lookup_cb - Required callback for local and remote acquisitions. It receives a BACnet.Protocol.DeviceObjectRef and returns {:ok, object}. The logger reads the configured property from that snapshot. Return {:error, %BACnet.Protocol.BACnetError{}} to record the Error Class and Error Code from a failed read. Callback exceptions and unexpected results are recorded as DEVICE/INTERNAL_ERROR. For a single Trend Log, the callback needs to enforce any read timeout.

      For Trend Log Multiple, each reference contributes one value or failure in array order, even if the lookups complete in a different order. An uninitialized object or device instance contributes PROPERTY/NO_PROPERTY_SPECIFIED without invoking the callback. The logger limits each read to the poll interval minus 10 milliseconds, clamped to 1 millisecond through 1 minute. A read that exceeds this limit contributes COMMUNICATION/TIMEOUT.

    • notification_receiver: Process.dest() - Optional. The recipient of buffer-full and BUFFER_READY messages. A host that uses lifecycle execution can use these messages to schedule execution when records arrive between its own executions. See add_object/3 for the message handling in each registration mode.

    • :state - Optional state from a previous logger instance. Use it to restore registered logs and their buffers after a restart. Startup options replace the options stored in the state. Supply a compatible state from the logger. For older states that lack Records_Since_Notification, the logger estimates it from the record sequence and Last_Notify_Record. That estimate can include records collected before a purge.

    • :supervisor - Optional task supervisor for acquisition and subscription tasks. By default, the logger starts those tasks without a supervisor.

    • :timezone - Optional timezone for timestamps and clock-aligned polling. Defaults to the application's :bacstack, :default_timezone configuration, or "Etc/UTC" when unset.

    • :timezone_database - Optional Calendar.TimeZoneDatabase implementation for timestamps, logging windows and offset tracking. Defaults to Calendar.get_time_zone_database/0 at startup. Configure a database that supports the zone when using a regional timezone.

    trigger_log(server, object, log)

    @spec trigger_log(
  server(),
  object(),
  BACnet.Protocol.Services.ConfirmedEventNotification.t()
  | BACnet.Protocol.Services.UnconfirmedEventNotification.t()
  | BACnet.Protocol.Services.ConfirmedCovNotification.t()
  | BACnet.Protocol.ObjectsUtility.bacnet_object()
  | [BACnet.Protocol.ObjectsUtility.bacnet_object()]
  | :interrupted
  | {:time_change, float()}
) :: :ok | {:error, term()}

    Records a supplied event, value or status in the specified log.

    When collection is disabled, data and time changes are ignored (returns :ok). The :interrupted status is recorded even when collection is disabled.

    For Trend Log Multiple, supply object snapshots in any order. The logger reads each configured reference in array order. Uninitialized references produce PROPERTY/NO_PROPERTY_SPECIFIED. An initialized reference with no matching snapshot produces OBJECT/UNKNOWN_OBJECT.

    Use sample/2 when the logger needs to acquire the values from its configured references before recording them.

    The accepted data depends on the type of log. All three types also accept :interrupted and {:time_change, seconds}, where seconds is a float.

    LogData
    Event LogConfirmed or unconfirmed event notification.
    Trend LogConfirmed or unconfirmed COV notification, or a source object snapshot.
    Trend Log MultipleA list of source object snapshots.

    update_object(server, object)

    @spec update_object(server(), object()) :: :ok | {:error, term()}

    Updates the following properties of the object in the trend logger:

    • buffer_size
    • cov_resubscription_interval (trend logs only)
    • enable
    • Intrinsic Reporting (notification threshold)
    • log_interval (trend logs only)
    • align_intervals and interval_offset (polled trend logs only)
    • logging_type (trend logs only)
    • start_time and stop_time
    • stop_when_full

    When updating buffer_size, the records in the buffer will transfer over to the new buffer, discarding any oldest records that would overfill the new buffer. Changing the monitored references of a trend log purges its history. Setting Stop_When_Full on a full buffer discards the oldest record and records that logging stopped. Changing Enable to true on a full buffer with Stop_When_Full already set returns {:error, :log_buffer_full}.

    update_object(server, object, property)

    @spec update_object(
  server(),
  object(),
  BACnet.Protocol.Constants.property_identifier()
) ::
  :ok | {:error, term()}

    Applies an explicit write to a log's collection or reporting settings.

    Uses the submitted value for that property and the logger's current settings for the other properties. Window writes apply both bounds together. Trend Log and Trend Log Multiple also accept acquisition settings and Buffer_Size. Logging_Type and Log_Interval apply together, as do Align_Intervals and Interval_Offset. Changing the monitored references purges the old history. Notification_Threshold edits preserve the last notification count. Standalone logs reevaluate the threshold after reporting property edits. A Buffer_Size write is rejected while Enable is true.

    An explicit write of true to Stop_When_Full records a stop if the buffer is full, including when Stop_When_Full was already true.

    An explicit write of true to Enable returns {:error, :log_buffer_full} if the log is full with Stop_When_Full set. This check runs in the logger.
