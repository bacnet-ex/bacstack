    BACnet.Protocol.ObjectTypes.Accumulator (bacstack v0.1.0-dev.2)

    View Source

    The Accumulator counts pulses from equipment such as an electricity, water or gas meter. Present_Value holds the running count. Prescale controls how many input pulses contribute to it, and Max_Pres_Value sets the rollover point. Optional properties report the pulse rate, record when the count was preset, or capture a sample for a logger.

    Object Description (ASHRAE 135)

    The Accumulator object type defines a standardized object whose properties represent the externally visible characteristics of a device that indicates measurements made by counting pulses.

    Accumulator objects that support intrinsic reporting shall apply the UNSIGNED_RANGE event algorithm.

    Count pulses

    Initialize the restored object with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 and an :initialization context. Deliver raw input pulse batches with record_pulses/3 and the prior result's state. The host needs to submit each batch once and retain the whole successful result before another operation. This module applies Prescale using integer arithmetic and carries the fractional remainder between batches. The divisor must be greater than zero. The count wraps modulo Max_Pres_Value plus one.

    An adapter that already maintains the absolute count can report it through update_property/3 with an :application_write trigger. Use a 1:1 Prescale when submitting batches of already prescaled pulses. Scale describes the engineering-unit conversion for clients reading Present_Value. The lifecycle leaves the count in its unsigned representation.

    Initialization preserves the supplied count and starts fresh runtime state. A new lifecycle, a changed Prescale or a Value_Set write starts a fresh fractional remainder.

    Measure the pulse rate

    Select Pulse_Rate or Limit_Monitoring_Interval to enable both properties. Intrinsic reporting also selects the pair. The interval is in seconds and must be positive. Pulse_Rate is the number of input pulses in the most recently completed fixed window, before prescaling. The host needs to supply a batch's acquisition time in the monotonic clock domain. A batch at the window boundary belongs to the new window. A completed window without pulses reports zero.

    The object execution host needs to arm the returned monotonic wakeup and deliver it with a :timer context. Replace the previous deadline after each successful step. An interval change starts a fresh window. The lifecycle also completes overdue windows on ordinary operations.

    Preset the count and simulate inputs

    When Value_Set is present, a write to it replaces Present_Value, stores the previous visible count in Value_Before_Change and stamps Value_Change_Time using the supplied device-local clock. This also happens when the same preset is written again. Value_Set is writable in either service state. Value_Before_Change and Value_Change_Time are read-only.

    Construct property candidates with update_property/3, call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 and execute the prepared candidate with the same context and prior state. The host needs to preserve the write origin, enforce service access and serialize operations. Rejection leaves the previous result in storage.

    Present_Value and Pulse_Rate are writable to BACnet clients while out of service. Incoming pulse batches are ignored and the rate timer is cancelled while isolated. Returning to service restores the retained count, including any Value_Set preset, and opens a new rate window.

    The host supplies Reliability from its input adapter. Inhibition exposes NO_FAULT_DETECTED while retaining the physical report. While out of service, either write origin can supply an alternate simulated Reliability. Refresh physical reports held only in runtime state after restarting.

    Qualified reads of Logging_Record

    Logging_Record holds the latest snapshot of the meter. It captures the acquisition time, the count at that time, the accumulated count since the preceding acquisition, and the status of that interval. The native property value is a one-element list containing a BACnet.Protocol.AccumulatorRecord. A host that needs a history can store each acquired snapshot separately.

    A qualified read of Logging_Record acquires a new snapshot and starts the next accumulation interval. Select Logging_Object when one local object should control those intervals. For example, an hourly logger can measure consumption between its samples while a dashboard or maintenance client reads the last hourly record at any time. Those readers see the retained timestamp and counts, and their reads leave the logger's interval intact. Without Logging_Object, every Logging_Record read acquires a new snapshot.

    Selecting Logging_Object also selects Logging_Record. Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 before getting the property. When a local object initiates a read, the host supplies its identifier as :reader_identifier in the BACnet.Protocol.ObjectExecution.Context options. A read qualifies when that identifier matches Logging_Object. Leave the option unset for network clients. Retain the successful result so the next read uses the same snapshot and interval state.

    Before the first acquisition, readers see STARTING with an unspecified timestamp and zero counts. The first qualified read captures the current time and count, with zero accumulated value, and establishes the baseline. Later acquisitions report the modular count delta. A Value_Set write is excluded from the delta and marks the interval RECOVERED when otherwise healthy. A delivered clock change marks the interval ABNORMAL. An exposed fault marks it FAILED and the acquired record reports zero delta. Changing Logging_Object or initializing the object starts a fresh baseline.

    With intrinsic_reporting: true, UNSIGNED_RANGE evaluates Pulse_Rate. The next wakeup includes rate sampling and reporting deadlines. After retaining the result, the host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1. Remote snapshots remain passive.

    The runnable walkthrough is examples/objects_lifecycle/accumulator_lifecycle.exs.

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
