    BACnet.Protocol.ObjectTypes.PulseConverter (bacstack v0.1.0-dev.2)

    View Source

    A Pulse Converter turns a pulse count into a quantity such as energy or water usage. It can accept batches of pulses or read a counter on another object. Present_Value is Count multiplied by Scale_Factor.

    Object Description (ASHRAE 135)

    The Pulse Converter object type defines a standardized object that represents a process whereby ongoing measurements made of some quantity, such as electric power or water or natural gas usage, and represented by pulses or counts, might be monitored over some time interval.

    Pulse Converter objects that support intrinsic reporting shall apply the OUT_OF_RANGE event algorithm.

    Direct and referenced acquisition

    Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 and an :initialization context. With no Input_Reference, deliver raw batches via record_pulses/3. Each pulse adds one to Count. An increase in Count due to acquisition stamps Update_Time with the supplied device-local time.

    Input_Reference identifies a local object and an INTEGER or Unsigned property. The object execution host supplies that property through the BACnet.Protocol.ObjectExecution.Context read callback. The lifecycle samples on initialization, a changed reference, a matching :object_changed notification or a :periodic trigger. An ordinary property read serves the retained result. The host needs to deliver source changes or choose a polling cadence. Execution requests no wakeup.

    The first valid sample establishes a source baseline and preserves the supplied Count. Later increases advance Count by the observed difference. A decrease establishes a fresh baseline. The callback needs to supply a monotonically increasing source if exact counting across resets or rollovers is required. A read failure preserves the last valid sample for the same reference. For a value that would otherwise be ambiguous, return its BACnet encoding so the converter can distinguish integer tags from other datatypes.

    Adjust the count

    An Adjust_Value write subtracts the quotient of the adjustment divided by Scale_Factor, truncated toward zero, from Count. The operation stores the written adjustment, copies the previous Count into Count_Before_Change, stamps Count_Change_Time and updates the coupled Present_Value. Repeating the same write applies another adjustment. Update_Time records acquisition and keeps its prior value when adjusting.

    Scale_Factor must be a finite, nonzero BACnet REAL. Count must be nonnegative and its product with Scale_Factor must fit in a finite REAL. An adjustment outside that domain returns {:error, {:property_out_of_range, :adjust_value}} before changing any property.

    Construct a candidate with update_property/3, prepare it with BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 and execute it with the same context and prior state. The host needs to serialize those operations and retain the complete successful result before exposing it.

    Out of service and Reliability

    Out_Of_Service allows explicit Present_Value and Reliability simulation. Direct pulse batches are ignored while isolated. Referenced acquisition can continue to update Count and Update_Time while leaving Present_Value and exposed Reliability isolated. The converter's Out_Of_Service property describes its own state. It remains independent of the referenced object's state. Adjust_Value still updates Count and its history during simulation. Returning to service recomputes Present_Value from Count.

    A referenced source selects Reliability. An unsupported source or datatype reports CONFIGURATION_ERROR. A failed read reports COMMUNICATION_FAILURE, and an increase that exceeds the count domain reports OVER_RANGE. Successful samples clear those reports. With a direct input, the application supplies Reliability. Reliability_Evaluation_Inhibit masks the report with NO_FAULT_DETECTED while retaining it. Explicit out-of-service Reliability writes from either origin can supply a simulated report while inhibited.

    With intrinsic_reporting: true, OUT_OF_RANGE evaluates the scaled Present_Value. After retaining the result, the host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1.

    Remote snapshots are passive. After a restart, initialize with restored properties and fresh state. The first successful reference read starts a new baseline.

    The runnable walkthrough is examples/objects_lifecycle/pulse_converter_lifecycle.exs.

    Examples

    Creating a Pulse Converter:

    iex> {:ok, pc} = BACnet.Protocol.ObjectTypes.PulseConverter.create(400, "Usage total", %{}); pc.object_name
"Usage total"

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
