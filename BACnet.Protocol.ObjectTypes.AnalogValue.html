    BACnet.Protocol.ObjectTypes.AnalogValue (bacstack v0.1.0-dev.2)

    View Source

    An Analog Value is used for an application value such as a setpoint, tuning constant or intermediate calculation. Both the local application and BACnet clients can write present_value, subject to the object's commandability and write rules.

    The object is frequently made commandable via a priority array so that multiple sources (operators, schedules, control loops, etc.) can compete for control of the value with well-defined priority arbitration and a relinquish default. The object carries a COV threshold (cov_increment) and can expose OUT_OF_RANGE reporting properties with intrinsic_reporting: true. Lifecycle execution maintains core value behaviour - event detection and notification delivery are separate. Typical properties include units and optional min/max present value limits.

    Object Description (ASHRAE 135)

    The Analog Value object type defines a standardized object whose properties represent the externally visible characteristics of an analog value. An "analog value" is a control system parameter residing in the memory of the BACnet Device.

    Analog Value objects that support intrinsic reporting shall apply the OUT_OF_RANGE event algorithm.

    Behaviour and Operation

    Analog Value objects represent in-memory analog parameters or setpoints. A non-commandable instance stores present_value directly. The local application supplies calculated values through update_property/3, and BACnet clients may write it through the host's service handler. There is no standardized periodic calculation, sensor acquisition or hardware output algorithm for this object.

    Optional commandability and priority arrays

    Supplying priority_array or relinquish_default selects commandability. The existing implicit relationship adds its partner, including when selected with add_property/3. Adding commandability replaces the previous direct value with the array's effective value. Removing the pair returns the instance to direct property updates.

    For a commandable instance, use set_priority/3 to implement writes to Present_Value from both BACnet clients and local applications. The lowest numbered non-nil slot wins. A nil command relinquishes only that slot, revealing the next command or relinquish_default when all slots are nil. Lower-priority commands are retained even while masked. A write without an explicit BACnet priority uses priority 16 - the host needs to pass that default to set_priority/3.

    Priority 6 is reserved for minimum on/off control and cannot be commanded or relinquished through set_priority/3. Analog Value has no minimum on/off timing. Lifecycle preflight rejects a stored non-nil slot 6 with {:error, {:invalid_configuration, :priority_6}}. The array is read-only to BACnet clients. Direct Present_Value updates bypass the command mechanism and must not be used for a commandable instance, including while out of service. The existing property operations keep the effective value synchronized when priorities or the relinquish default change.

    Out of service and write origin

    out_of_service: true prevents normal local software from modifying Present_Value. BACnet.Protocol.ObjectExecution.Context distinguishes these updates with {:application_write, property, array_index, priority}. Lifecycle preparation rejects local Present_Value writes while out of service, including same-value and masked commands. It also rejects indirect local changes to the effective value, such as a relinquish-default edit that changes Present_Value. A masked configuration edit that leaves the effective value unchanged is allowed.

    BACnet writes use {:property_write, property, array_index, priority} and remain available for simulation while out of service. Commandable instances still arbitrate these writes. A local adapter handling a BACnet request needs to preserve that BACnet origin. Local value production can resume after returning to service.

    Lifecycle and host contract

    The object execution host is the integrating application or higher-level BACnet stack that retains the object and its runtime state, serializes operations and supplies their context. This module starts no process and invokes no host I/O callbacks.

    Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 and the :initialization trigger. Retain the full returned result. For each write, construct a candidate through this module's property operations, call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3, commit the prepared object and execute it with the same context and previous runtime state before exposing the operation. Deliver every accepted write, including same-value writes. Raw property operations do not enforce lifecycle origin checks or execute the lifecycle themselves.

    The host still needs to enforce service permissions, read-only annotations, array indices and BACnet priority rules. Preparation is pure and rejected writes leave the original object and state unchanged. Execute returns no replacement result on error. Initialization is required for local operations - missing, malformed or other-instance runtime state returns {:error, :invalid_execution_state}.

    Every successful execution returns next_execution: nil. No timer or periodic polling is required for this core behaviour. The host needs to cancel any superseded request when retaining that result. Reads can use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 and then get_property/2. Wall and monotonic clocks do not drive arithmetic here. After a restart, initialize from restored object properties with fresh context and state. Runtime-only suppressed reliability reports cannot be recovered from a property that currently exposes NO_FAULT_DETECTED - the application needs to supply a fresh report if necessary.

    Reliability and status flags

    The application supplies reliability from the health of its value source - for example, a failed calculation or missing dependency. No source fault is inferred from a rejected write, a min/max validation error or an invalid runtime state. The existing property mechanics propagate Reliability into the FAULT status flag, Event_State into IN_ALARM and Out_Of_Service into OUT_OF_SERVICE. OVERRIDDEN remains a local indication that the host needs to supply when applicable.

    When selected, reliability_evaluation_inhibit exposes NO_FAULT_DETECTED while true, except for an explicitly supplied or written Reliability while out of service. The lifecycle retains the latest supplied reliability report and restores it when inhibition ends. Entering out of service alone does not turn a previously suppressed report into a simulation value. Returning to service while inhibited masks that alternate value again. Reliability reports may still be supplied while out of service - the software-value isolation rule applies to Present_Value.

    Configuration, intrinsic reporting and COV

    units, resolution, min_present_value and max_present_value describe the engineering value and its usable range. When both min/max properties are present, the existing range validator applies to values, priority commands and relinquish defaults. The lifecycle does not add a control formula, unit conversion or rounding.

    With intrinsic_reporting: true, execution evaluates OUT_OF_RANGE using the effective value and enabled limits. Reliability faults take precedence. Event and recovery delays use monotonic time. The host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1 after retaining the result. cov_increment represents the COV threshold for the host's subscriptions and delivery.

    Remote Analog Values

    Remote snapshots are passive. Lifecycle execution preserves the supplied object and context state, requests no wakeup and invokes no host callbacks. Preparing local writes to a remote snapshot returns {:error, :operation_not_available_for_remote_objects}.

    Complete write example

    This example supplies a local application value and retains the resulting state. For a commandable instance, construct the candidate with set_priority/3 instead.

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> {:ok, object} = BACnet.Protocol.ObjectTypes.AnalogValue.create(10, "Room setpoint", %{present_value: 21.0, units: :degrees_celsius})
iex> start = Context.new(:initialization, now: ~U[2026-11-08 10:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, start)
iex> write = Context.new({:application_write, :present_value, nil, nil}, now: ~U[2026-11-08 10:00:01Z], monotonic_time: 1000, state: stored.state)
iex> {:ok, candidate} = BACnet.Protocol.ObjectTypes.AnalogValue.update_property(stored.object, :present_value, 22.0)
iex> {:ok, prepared} = Lifecycle.prepare_write(stored.object, candidate, write)
iex> stored = %{stored | object: prepared}
iex> {:ok, stored} = Lifecycle.execute(stored.object, write)
iex> {stored.object.present_value, stored.next_execution}
{22.0, nil}

    A runnable walkthrough is examples/objects_lifecycle/analog_value_lifecycle.exs.

    Examples

    Creating a simple Analog Value:

    iex> {:ok, av} = BACnet.Protocol.ObjectTypes.AnalogValue.create(10, "Setpoint", %{units: :percent}); av.units
:percent

    Selecting intrinsic reporting properties:

    iex> {:ok, av} = BACnet.Protocol.ObjectTypes.AnalogValue.create(11, "CalcResult", %{}, intrinsic_reporting: true); is_number(av.high_limit)

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}

  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
