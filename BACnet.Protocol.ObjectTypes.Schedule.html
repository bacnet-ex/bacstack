    BACnet.Protocol.ObjectTypes.Schedule (bacstack v0.1.0-dev.2)

    View Source

    A Schedule selects a value from a weekly timetable or an exception and writes it to configured BACnet properties. Use one for occupancy setpoints, lighting scenes or holiday overrides. Several schedules can share a holiday list through a BACnet.Protocol.ObjectTypes.Calendar.

    A weekly schedule contains seven daily lists of time/value pairs, Monday through Sunday. Exception schedules override those lists on dates selected by inline calendar entries or local Calendar references. present_value is the currently selected primitive BACnet value.

    Object Description (ASHRAE 135)

    The Schedule object type defines a standardized object used to describe a periodic schedule that may recur during a range of dates, with optional exceptions at arbitrary times on arbitrary dates. The Schedule object also serves as a binding between these scheduled times and the writing of specified "values" to specific properties of specific objects at those times.

    Behaviour and Operation

    execute/2 implements the calculation and target writes. The object execution host is the integrating application or higher-level BACnet stack that owns this object and drives its lifecycle. The host needs to supply time, retain results, deliver triggers and arrange wakeups. It does not need to implement a separate Schedule evaluator.

    For each active day, the Schedule selects the latest time/value pair at or before the supplied local time. Entries may be supplied in any order, but each time must be specific and unique within its daily or special-event list. Values do not carry over from the preceding day.

    Matching exceptions are considered in order of priority, then exception array index. The first exception contributing a non-NULL value wins. A NULL contribution falls through to lower-priority exceptions, today's weekly value and finally schedule_default. Event priority chooses an exception - priority_for_writing independently chooses the target command priority.

    effective_period bounds automatic scheduling. On entry, calculation and target writes occur even when the selected value equals the stored value. Outside that period, the previous present_value is retained. Leaving the period or entering out-of-service does not automatically relinquish earlier target commands.

    Configuration and Value Datatypes

    The weekly property must contain seven BACnet.Protocol.DailySchedule elements when present. An empty seven-day weekly schedule is valid. If it is absent, exception_schedule must contain at least one BACnet.Protocol.SpecialEvent, whose time/value list may itself be empty. Creation supplies an empty weekly schedule by default. A host resizing an exception array needs to initialize new special events with empty time/value lists and valid period/priority fields.

    Values use primitive BACnet.Protocol.ApplicationTags.Encoding structs. All primitive application tags in BACnet.Protocol.ApplicationTags.primitive_type/0 are supported, including NULL. Non-NULL weekly, exception and default values must share one BACnet datatype. An all-NULL configuration is valid. Tagged/constructed values and deferred BACnet.Protocol.ApplicationTags.Encoding encoder functions are rejected during execution preflight.

    Local target compatibility uses each resolved object's property type map and encoding annotations. REAL and Double remain distinct, as do ENUMERATED and Unsigned. For example, a binary output's ENUMERATED 0/1 becomes the Boolean representation expected by its property functions. An incompatible tag is not silently coerced to the target datatype. Primitive property codecs are used when declared, with the outgoing tag checked for consistency. Local validation uses BACnet.Protocol.ObjectsUtility.cast_property_to_value/4 with the identifier obtained from the target module's object-identifier getter. NULL time/value entries select a fallback - a NULL schedule_default can itself be written and is included in target validation. A NULL command relinquishes the selected target priority.

    Each target write callback receives the original BACnet.Protocol.ApplicationTags.Encoding. A local host adapter needs to cast it through BACnet.Protocol.ObjectsUtility.cast_property_to_value/4 with the target's object identifier before applying the property write or command. A NULL commandable present_value write relinquishes the selected priority through the target module's priority setter, using nil. Handle this before ordinary property casting. Use allow_partial: true when casting an array element. Index zero belongs to length validation and resizing in the write path. Remote adapters can pass the encoding directly to BACnet.Stack.ClientHelper.write_property/6, retaining the reference's property, array index and write priority. The host needs to resolve device identifiers to network destinations and bound transport waits. Schedule does not look up remote object models or infer remote datatype support - remote write responses report failures.

    Target references form an Elixir list, matching BACnetLIST semantics. Targets may be scalar properties or indexed array elements. An array index must exist; index zero is accepted only for a variable array's Unsigned length. The host write callback needs to implement that property's resize/default-initialization rules. A whole structured array is not a primitive scheduled value.

    Lifecycle Execution

    Use BACnet.Protocol.ObjectExecution.Lifecycle around the module-owned callbacks. Preparation validates configuration and capabilities without host I/O. Duplicate times return {:error, {:duplicate_entry, property}}. Other malformed schedules return {:error, {:invalid_configuration, property}}. Mixed non-NULL configuration datatypes are rejected by write preparation with {:error, :inconsistent_datatypes}. Property functions validate representation - an update alone does not run this lifecycle or command targets.

    The host needs to serialize each object's operations and supply:

    • now in the device's configured timezone, timezone_database supporting that zone, current monotonic milliseconds, the trigger and the last returned opaque runtime state.
    • write_property when the target list is nonempty. Writes receive the selected encoding, the complete target reference and priority_for_writing.
    • lookup_object when any target is local. Lookup must return the actual local object, including its type map and property annotations. Remote-only target lists need no lookup.
    • read_property when automatic scheduling uses Calendar references. Calendar reads must be fresh through the lifecycle and use the enclosing operation's supplied time. Running Calendar first on some previous tick does not establish freshness.
    • device_identifier, set to the containing Device's identifier to recognize explicit self-device references, or nil when not needed. Recognized self references are normalized to local references for host I/O. Other device-qualified references remain remote, with their device identifier preserved. Without a local identity, all device-qualified references are forwarded as remote references.

    No object-specific context.options are needed. Empty target lists need no lookup or write callback. Local Calendar references contain only an ObjectIdentifier and always resolve locally.

    Triggers, commits and target writes

    EventRequired interaction
    Start or restartExecute with :initialization and fresh runtime state. Active initialization commands the selected value.
    Proposed property writeBuild a candidate through property functions, then call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3. Commit the accepted candidate and execute with the same property-write context, including same-value writes.
    Computed readCall BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2, retain its result, finish continuations, then call get_property/2.
    Requested deadlineCheck BACnet.Protocol.ObjectExecution.Wakeup.due?/2 with fresh supplied time and execute with :timer.
    Clock or timezone changeExecute with :clock_change, including relevant timezone-offset/DST changes, and replace the previous wakeup.
    Calendar edit/value changeDeliver {:object_changed, reference} to affected Schedules.

    Before target writes, execution resolves and checks all targets. It publishes the calculated present_value and a pending write plan in a result requesting :immediate. The host needs to commit that result, then execute with :continuation before processing another external operation. This makes the new Schedule value visible to target callbacks. The continuation attempts valid targets in list order and retains each failure while continuing through the rest.

    A selected-value change, active initialization, effective-period entry or return to service commands the targets. In-service edits of the target list or write priority also send the current value to the current targets. Removed targets are not automatically relinquished. Unchanged periodic calls and reads do not repeat writes. A successful revalidation after a configuration fault resynchronizes active targets; unchanged write failures are retained until a later command or explicit reinitialization, without automatic retries on every tick.

    Out-of-service and reliability

    In service, host access checks and write preparation reject client writes to present_value. While out_of_service is true, automatic calculation stops and present_value becomes writable. A manual change still commands all configured targets at priority_for_writing. A same-value manual write passes through execution but does not create another value change. Changing other configuration while out of service does not substitute an automatic value.

    Manual control also remains available when the automatic configuration has inconsistent datatypes. The manual value is checked against the targets independently, while reliability continues to report the automatic configuration fault.

    Target lookup, writability, type and index failures set reliability to :configuration_error. Invalid targets are skipped and valid targets are still attempted. Calendar-read failures and inconsistent configuration datatypes also produce a retained configuration fault, holding the previous value until calculation can recover. Property/type/access rejections from target writes also set :configuration_error. Other write-operation failures set :communication_failure unless a configuration failure also occurred. The returned opaque state retains reference/reason pairs. Property operations maintain the corresponding status flags.

    These operational faults return successful results containing the updated reliability and state. Pure preflight errors supply no replacement result. The host needs to preserve the previous result on rejection, or an already accepted property write if execution fails after commit. The host also needs to enforce target service permissions and reserved command-priority rules.

    reliability_evaluation_inhibit masks automatic reliability evaluation with :no_fault_detected, except for an alternate Reliability explicitly written while out of service. Explicit simulation writes can use either BACnet or application origin. Failure details remain in runtime state. With intrinsic_reporting: true, changes in Reliability can generate FAULT and NORMAL transitions. The host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1 after retaining the result. Local and remote target writes are supported through host callbacks. Remote Schedule snapshots execute passively, preserving their object and supplied state with no next-execution request.

    Wakeups and state ownership

    Each automatic step requests the next potential time/value transition or local midnight as a wall-clock BACnet.Protocol.ObjectExecution.Wakeup. Exception lists can produce extra checks even when their dates do not match - unchanged checks do not repeat commands. Ambiguous local times include both occurrences and use the first future instant. A time in a gap resolves to the first instant after that gap. The host needs to report clock corrections and timezone-offset changes promptly so calculation reflects a repeated or skipped local hour.

    Out-of-service execution requests no timer. Each successful result replaces the previous request, including cancellation with nil. Runtime state belongs to this module and includes prior effective/service state, pending writes and retained failures. Pass it back unchanged for that same instance. After a VM restart use nil and initialization with current clocks. See BACnet.Protocol.ObjectExecution.Lifecycle for complete timer-arming and continuation code.

    Examples

    This complete example calculates a daily lighting schedule without targets. A host with targets must also supply the callbacks and drain immediate continuations described above.

    iex> alias BACnet.Protocol.ApplicationTags.Encoding
iex> alias BACnet.Protocol.{BACnetArray, BACnetTime, DailySchedule, TimeValue}
iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.Schedule
iex> on = Encoding.create!({:enumerated, 1})
iex> off = Encoding.create!({:enumerated, 0})
iex> day = %DailySchedule{schedule: [
...>   %TimeValue{time: BACnetTime.from_time(~T[08:00:00]), value: on},
...>   %TimeValue{time: BACnetTime.from_time(~T[18:00:00]), value: off}]}
iex> {:ok, schedule} = Schedule.create(600, "Lighting", %{
...>   weekly_schedule: BACnetArray.from_list(List.duplicate(day, 7), true),
...>   schedule_default: off})
iex> context = %Context{
...>   device_identifier: nil,
...>   now: ~U[2026-11-09 08:00:00Z],
...>   timezone_database: Calendar.UTCOnlyTimeZoneDatabase,
...>   monotonic_time: 0,
...>   trigger: :initialization,
...>   state: nil,
...>   lookup_object: nil,
...>   read_property_multiple: nil,
...>   read_property: nil,
...>   write_property: nil,
...>   options: []}
iex> {:ok, stored} = Lifecycle.execute(schedule, context)
iex> stored.object.present_value
%Encoding{encoding: :primitive, type: :enumerated, value: 1, extras: []}
iex> DateTime.to_iso8601(stored.next_execution.wall_time)
"2026-11-09T18:00:00.000000Z"
iex> context = %{context | now: ~U[2026-11-09 18:00:00Z],
...>   monotonic_time: 36_000_000, state: stored.state, trigger: :timer}
iex> {:ok, stored} = Lifecycle.execute(stored.object, context)
iex> Schedule.get_property(stored.object, :present_value)
{:ok, %Encoding{encoding: :primitive, type: :enumerated, value: 0, extras: []}}

    For a runnable example with a Calendar, a commandable binary output, fresh reads, target writes, out-of-service manual control and deadline delivery, run mix run examples/objects_lifecycle/schedule_lifecycle.exs from the repository root. See the schedule lifecycle in the examples directory for the walkthrough and integration expectations.

    @type common_object_opts() ::

  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
