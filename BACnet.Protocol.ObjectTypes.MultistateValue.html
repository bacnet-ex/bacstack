    BACnet.Protocol.ObjectTypes.MultistateValue (bacstack v0.1.0-dev.2)

    View Source

    A Multistate Value represents an application mode, stage or sequence position. Its value is a state number between 1 and Number_Of_States. The application defines what each number means and can expose labels through state_text.

    Unlike an Input or Output object, this object has no prescribed hardware acquisition or output operation. Its value producer and consumer belong to the application. Optional commandability allows schedules, operators and control logic to compete for control through a priority array and relinquish default.

    Object Description (ASHRAE 135)

    The Multi-state Value object type defines a standardized object whose properties represent the externally visible characteristics of a multi-state value. A "multi-state value" is a control system parameter residing in the memory of the BACnet Device.

    Multi-state Value objects that support intrinsic reporting shall apply the CHANGE_OF_STATE event algorithm.

    Values and optional commandability

    number_of_states and present_value must be positive, and Present_Value cannot exceed Number_Of_States. A non-commandable instance accepts direct values through update_property/3. This implementation permits BACnet writes while in service as well as out of service. The host still needs to enforce its service permissions.

    Selecting priority_array or relinquish_default adds the other through their implicit relationship. The effective array value replaces any previous direct value. Removing the pair returns the object to direct value updates.

    For commandable instances, construct Present_Value writes with set_priority/3 from either BACnet or application origin. The lowest numbered non-nil slot wins. nil relinquishes only that slot, revealing another command or Relinquish_Default. Masked commands remain stored. The host needs to pass priority 16 for a BACnet command without an explicit priority. Direct Present_Value updates are protected, including while out of service. Priority_Array is read-only to BACnet clients.

    Priority 6 is reserved for minimum on/off control. Multistate Value has no minimum on/off timer, and set_priority/3 rejects commands and relinquishment at priority 6. Lifecycle preflight rejects a stored non-nil slot 6 with {:error, {:invalid_configuration, :priority_6}}. Other slots and Relinquish_Default must all remain within 1..Number_Of_States, even while masked.

    Out of service and write origin

    out_of_service: true isolates Present_Value from normal local software updates. Use {:application_write, property, array_index, priority} for that origin. Lifecycle preparation rejects local Present_Value writes while isolated, including same-value and masked commands. Indirect local changes to the effective value are also rejected. A masked configuration edit that leaves the effective value unchanged is allowed. Preparation checks both the original and candidate states - resume service before supplying the next local value in a separate operation.

    BACnet requests use {:property_write, property, array_index, priority} and remain available for simulation. Command arbitration continues while isolated. A local callback handling a BACnet request needs to preserve that BACnet origin. Named and numeric property identifiers are supported by lifecycle origin and priority checks. Returning to service preserves the effective value until another accepted write.

    State count and label changes

    For local objects, update_property/3 synchronizes Number_Of_States and a selected State_Text array. Increasing the count retains existing labels and appends empty strings. Decreasing it truncates labels only if Present_Value, every stored priority command and Relinquish_Default still fit. State_Text updates must match the existing count and never change Number_Of_States. No labels are selected implicitly when the optional property is absent. The array retains its fixed/variable representation.

    The specification leaves value reconciliation after a count change to the implementation. This implementation rejects an invalidating reduction instead of clamping values or clearing commands. Reconcile values, priorities and the default first, then reduce the count. Rejection returns no partial object. Lifecycle preflight also rejects inconsistent count/value/label candidates with {:error, {:invalid_configuration, property}}. State_Text needs a string at every position - sparse unknown labels are rejected.

    Number_Of_States remains read-only to BACnet clients. The host needs to enforce that service access and turn supported indexed State_Text edits into a complete array before calling the property operation. An array element replacement can use BACnet.Protocol.BACnetArray.set_item/3. Updating a property does not execute its lifecycle or determine write origin.

    Lifecycle and host contract

    The object execution host is the integrating application or higher-level BACnet stack that retains object and runtime state, serializes operations and supplies their context. This module starts no process and invokes no host I/O callbacks.

    Initialize local objects with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2 and an :initialization context. Initialization preserves supplied direct values or effective commands and establishes the Reliability baseline. Retain the full result. For each write, construct a candidate through this module's property operations, call BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3, commit the prepared object while retaining the previous runtime state, and execute with the same context before exposing the operation. Retain the complete result before the next operation. Deliver every accepted write, including same-value and masked commands.

    The host still needs to enforce service permissions, read-only annotations, array indices and BACnet priority rules. Preparation is pure. On error, retain the original object, runtime state and wakeup - no replacement result is supplied. Missing, malformed or other-instance state returns {:error, :invalid_execution_state}. Raw property operations do not perform lifecycle preparation or execution.

    Reads can use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2, retain its result, then call get_property/2. Every successful execution returns next_execution: nil. The host needs to cancel a superseded wakeup when retaining that result. This core behaviour has no periodic calculation or timing requirement. Wall-clock changes and monotonic time do not drive arithmetic here.

    Reliability and reporting

    The application supplies Reliability from the health of its value source, such as a failed calculation or missing dependency. A rejected write or configuration does not diagnose a source fault. Property propagation maintains FAULT from Reliability, IN_ALARM from the supplied Event_State and OUT_OF_SERVICE from Out_Of_Service. OVERRIDDEN remains a local indication for the host to supply when applicable.

    Reliability_Evaluation_Inhibit exposes NO_FAULT_DETECTED while true, except for an explicitly supplied or written out-of-service Reliability. The lifecycle retains the latest report for restoration when inhibition ends. Entering out of service alone does not expose an earlier suppressed report. Explicit Reliability simulation is accepted from both origins, including while inhibited. Returning to service while inhibited masks that simulation again. The host needs to isolate automatic source Reliability reports while simulating - application origin alone does not express intent.

    With intrinsic_reporting: true, CHANGE_OF_STATE compares Present_Value with Alarm_Values. FAULT_STATE uses Fault_Values when reliability evaluation is enabled. A reliability fault takes precedence over an alarm match. After retaining the result, the host retrieves transitions with BACnet.Protocol.ObjectExecution.EventReporting.transition/1.

    With Fault_Values configured, the algorithm supplies Reliability while evaluation is enabled. To retain an explicit out-of-service Reliability write, set Reliability_Evaluation_Inhibit to true before the write.

    Restart and remote snapshots

    After restart, initialize from restored properties with fresh context and runtime state. Supplied out-of-service Reliability is retained for simulation. A suppressed report held only in old runtime state cannot be recovered from a property exposing NO_FAULT_DETECTED - the application needs to supply a fresh report when necessary.

    Remote snapshots remain passive. Lifecycle execution preserves their object and context state without callbacks or wakeups. Local write preparation returns {:error, :operation_not_available_for_remote_objects}. Property synchronization described above applies to local objects.

    Complete write example

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> {:ok, object} = BACnet.Protocol.ObjectTypes.MultistateValue.create(5, "Operating mode", %{number_of_states: 3, relinquish_default: 1})
iex> start = Context.new(:initialization, now: ~U[2026-11-08 10:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, start)
iex> command = Context.new({:application_write, :present_value, nil, 16}, now: start.now, monotonic_time: 0, state: stored.state)
iex> {:ok, candidate} = BACnet.Protocol.ObjectTypes.MultistateValue.set_priority(stored.object, 16, 2)
iex> {:ok, prepared} = Lifecycle.prepare_write(stored.object, candidate, command)
iex> stored = %{stored | object: prepared}
iex> {:ok, stored} = Lifecycle.execute(stored.object, command)
iex> {stored.object.present_value, stored.next_execution}
{2, nil}

    @type common_object_opts() ::

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
