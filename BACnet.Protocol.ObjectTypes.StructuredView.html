    BACnet.Protocol.ObjectTypes.StructuredView (bacstack v0.1.0-dev.2)

    View Source

    A Structured View organizes object references into a hierarchy that clients can browse, such as floor, air handler and supply temperature. The node_type and node_subtype describe the kind of node. The subordinate_list holds references to its children, which can themselves be Structured Views.

    The structure is completely independent of the flat object_list in the Device object - it is an additional navigation aid. Views can represent physical hierarchy, functional systems, graphics pages, or any other grouping the implementer desires.

    Object Description (ASHRAE 135)

    The Structured View object type defines a standardized object that provides a container to hold references to subordinate objects, which may include other Structured View objects, thereby allowing multilevel hierarchies to be created.

    Behaviour and Operation

    Structured View objects are passive organisational containers. They do not contain or duplicate data from the referenced objects - each entry in subordinate_list is a reference.

    The device or a configuration tool populates the tree. Clients use the view for navigation, graphics binding, or hierarchical browsing instead of (or in addition to) the flat object_list on the Device object. The view may reference objects that are not in the device's own object list (for proxy / remote views).

    Subordinate list and annotations

    Subordinate_List and Subordinate_Annotations are BACnet.Protocol.BACnetArray properties. When annotations are present, each annotation describes the subordinate at the same one-based index. Provide arrays of equal size when creating a local object or adding annotations. Each array needs a value at every index.

    update_property/3 resizes the other array when either array changes size, as required by ASHRAE 135-2012 Clauses 12.29.7 and 12.29.8. It keeps entries at retained positions and discards entries beyond the new end. Growing the annotation array adds empty strings. Growing the subordinate array adds uninitialized references with object instance 4194303. Use configured_subordinates/1 to skip those references while retaining the original one-based BACnet array indices for annotation lookup.

    Lifecycle and host contract

    Initialize or validate a restored view with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2. It checks that both arrays have the same size when annotations are present. A view needs no runtime state, host I/O or wakeup. It has no commandability or event generation. Remote snapshots retain the property values received from the device.

    The object execution host needs to enforce write permissions and BACnet array indices. For an accepted element write, the host needs to replace the element with BACnet.Protocol.BACnetArray.set_item/3 and submit the resulting array through update_property/3. Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 to check the candidate and retain the whole object on success so both arrays are visible together.

    Developer Implementation Notes

    The application decides which objects belong in each view and updates the references when the hierarchy changes. For example, if a deleted object should disappear from the hierarchy, update each view that references it. Resizing preserves annotations by array index. If the application moves references to different indices, it needs to move their annotations too.

    A BACnet client can edit the hierarchy when the host exposes the relevant properties as writable and accepts the writes. The host can use property_writable?/2 when checking write access.

    A client browsing the hierarchy can start at a root view and follow its configured references. A reference without a device identifier points to an object on the same device as the view. A device-qualified reference can point to an object on another device.

    Typical uses

    • Physical hierarchies such as site, building, floor, room, and equipment.
    • Functional systems such as a chilled water system with pumps, valves, and sensors spread across several controllers.
    • Graphics pages that group the points needed for each display.
    • Proxy views that group references to objects on another device.

    Examples

    Create an empty Structured View.

    iex> alias BACnet.Protocol.BACnetArray
iex> alias BACnet.Protocol.ObjectTypes.StructuredView
iex> {:ok, view} = StructuredView.create(1700, "BuildingView", %{node_type: :device})
iex> BACnetArray.get_item(view.subordinate_list, 0)
{:ok, 0}

    Add a second annotation to reserve a subordinate slot. The new slot has instance 4194303, so only the fan appears among configured subordinates. Shrinking Subordinate_List back to one entry removes the spare annotation.

    iex> alias BACnet.Protocol.{BACnetArray, DeviceObjectRef, ObjectIdentifier}
iex> alias BACnet.Protocol.ObjectTypes.StructuredView
iex> fan = %DeviceObjectRef{
...>   device_identifier: nil,
...>   object_identifier: %ObjectIdentifier{type: :binary_output, instance: 8}
...> }
iex> references = BACnetArray.from_list([fan])
iex> {:ok, view} = StructuredView.create(10, "Ventilation", %{
...>   node_type: :equipment,
...>   subordinate_list: references,
...>   subordinate_annotations: BACnetArray.from_list(["Supply fan"])
...> })
iex> annotations = BACnetArray.from_list(["Supply fan", "Spare"])
iex> {:ok, grown} = StructuredView.update_property(view, :subordinate_annotations, annotations)
iex> BACnetArray.get_item(grown.subordinate_list, 0)
{:ok, 2}
iex> {:ok, spare} = BACnetArray.get_item(grown.subordinate_list, 2)
iex> spare.object_identifier.instance
4194303
iex> {:ok, configured} = StructuredView.configured_subordinates(grown)
iex> configured == [{1, fan}]
true
iex> {:ok, shortened} = StructuredView.update_property(grown, :subordinate_list, references)
iex> BACnetArray.to_list(shortened.subordinate_annotations)
["Supply fan"]

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
