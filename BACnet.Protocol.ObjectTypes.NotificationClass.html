    BACnet.Protocol.ObjectTypes.NotificationClass (bacstack v0.1.0-dev.2)

    View Source

    A Notification Class determines where an event notification should go and how to send it. Event sources reference the class by its Notification_Class number. The class defines these settings.

    • per-transition priorities (to-offnormal, to-fault, to-normal)
    • whether each transition requires operator acknowledgment
    • the recipients and their valid days, time windows, and process identifiers

    Because many objects can share the same Notification Class, a site can enforce consistent alarming policy (e.g. "all critical alarms go to the BMS at priority 8 and require ack") without repeating the recipient list in every object.

    Object Description (ASHRAE 135)

    The Notification Class object type defines a standardized object that represents and contains information required for the distribution of event notifications within BACnet systems.

    Behaviour and Operation

    Use routing_plan/3 when an event transition needs routing. Supply the transition and the device's local date and time. A destination is eligible when its day and transition bits are set and the time is within its inclusive window. Each matching BACnet.Protocol.Destination retains the recipient, process identifier, and confirmed or unconfirmed delivery setting. The plan includes the configured transition priority and acknowledgment flag and maps the priority to a BACnet network priority.

    Use add_destination/2 and remove_destination/2 to edit Recipient_List one entry at a time. Entries are matched by the complete destination, so a recipient can have multiple entries with different delivery settings.

    Host responsibilities

    The object execution host needs to look up the class referenced by the event source and apply the source's Event_Enable and Notify_Type rules. It needs to resolve recipient device identifiers, deliver the notifications, and track acknowledgments on the event source. The plan reports the class's acknowledgment flag. When building a notification, the host needs to apply source-specific rules for Access Point and Alert Enrollment and omit AckRequired from acknowledgment notifications.

    Recipient_List entries do not expire. The host needs to persist the configured list across restarts. If the host exposes Recipient_List as read-only, it needs to meet the local forwarder or local broadcast requirements in ASHRAE 135-2016 Clause 12.21.8. Recipient_List filtering applies to external notification distribution. Delivery to local objects such as Event Logs is handled by the host under Clause 13.2.5.

    For a BACnet RemoveListElement request, a false removal result indicates LIST_ELEMENT_NOT_FOUND. The host needs to apply access checks and commit a multi-element update only when the entire request succeeds.

    Routing needs no lifecycle state or timer. Event detection and notification delivery are driven by the integrating application.

    Examples

    Route a Monday morning TO_OFFNORMAL transition to a confirmed recipient.

    iex> alias BACnet.Protocol.{BACnetTime, DaysOfWeek, Destination, EventTransitionBits}
iex> alias BACnet.Protocol.{NotificationClassPriority, ObjectIdentifier, Recipient}
iex> alias BACnet.Protocol.ObjectTypes.NotificationClass
iex> offnormal = %EventTransitionBits{to_offnormal: true, to_fault: false, to_normal: false}
iex> workstation = %Recipient{
...>   type: :device,
...>   device: %ObjectIdentifier{type: :device, instance: 123},
...>   address: nil
...> }
iex> destination = %Destination{
...>   recipient: workstation,
...>   process_identifier: 10,
...>   issue_confirmed_notifications: true,
...>   transitions: offnormal,
...>   valid_days: DaysOfWeek.from_bitstring({true, true, true, true, true, false, false}),
...>   from_time: BACnetTime.from_time(~T[08:00:00]),
...>   to_time: BACnetTime.from_time(~T[18:00:00])
...> }
iex> {:ok, class} = NotificationClass.create(700, "Alarms", %{
...>   notification_class: 700,
...>   priority: %NotificationClassPriority{to_offnormal: 8, to_fault: 80, to_normal: 220},
...>   ack_required: offnormal
...> })
iex> {:ok, class} = NotificationClass.add_destination(class, destination)
iex> plan = NotificationClass.routing_plan(class, :to_offnormal, ~U[2026-11-09 08:00:00Z])
iex> {plan.priority, plan.network_priority, plan.ack_required}
{8, :life_safety_message, true}
iex> [target] = plan.destinations
iex> {target.process_identifier, target.issue_confirmed_notifications}
{10, true}
iex> {:ok, class, true} = NotificationClass.remove_destination(class, destination)
iex> {:ok, ^class, removed} = NotificationClass.remove_destination(class, destination)
iex> removed
false

    common_object_opts()

    @type common_object_opts() ::
  {:allow_numeric_constants, boolean()}
  | {:allow_unknown_properties, boolean()}
  | {:ignore_unknown_properties, boolean()}
  | {:revision,
     BACnet.Protocol.Constants.protocol_revision() | non_neg_integer()}
  | {:skip_property_validation_remote_object, boolean() | :value}

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.

    routing_plan(object, transition, local_datetime)

    @spec routing_plan(
  t(),
  BACnet.Protocol.Constants.event_transition_bit(),
  DateTime.t()
) ::
  routing_plan()

    Selects the destinations and class settings for a transition.

    Pass a datetime expressed in the device's local timezone. The date determines the weekday and the time is evaluated at BACnet's hundredth-of-a-second precision. Both endpoints are included. Each window applies within a single day. To cover both sides of midnight, configure separate windows.

    A transition with no matching recipients still returns its priority and acknowledgment settings. Network priority follows ASHRAE 135-2016 Table 13-6.
