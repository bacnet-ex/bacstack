    BACnet.Protocol.ObjectTypes.Averaging (bacstack v0.1.0-dev.2)

    View Source

    An Averaging object tracks the minimum, maximum and arithmetic mean of a property over a moving window. It can also report variance and the timestamps of the extrema. For example, sample the same temperature periodically to see how far it varies over the last hour.

    object_property_reference identifies a local or remote property. Every window_interval / window_samples seconds, execution attempts to acquire that property through the host's read callback. The latest window_samples attempts form the window. A failed acquisition occupies a missed slot rather than contributing a zero value.

    Object Description (ASHRAE 135)

    The Averaging object type defines a standardized object whose properties represent the externally visible characteristics of a value that is sampled periodically over a specified time interval.

    Statistics and sample values

    min_value, max_value and average_value describe the valid samples in the current window. attempted_samples counts retained attempts and valid_samples counts successful acquisitions, so their difference gives the missed samples. Both counts stop growing when the window is full. Displacing an attempt also removes its value from the statistics.

    Optional variance_value uses population variance, dividing the sum of squared deviations by the valid sample count. A single finite sample has zero variance. Optional min_value_timestamp and max_value_timestamp record the acquisition time of each extremum. When values tie, the oldest retained sample's timestamp wins. These choices are implementation policies - the object clause does not prescribe the variance formula or timestamp tie policy.

    Accepted inputs are native booleans, integers and REAL floats, or primitive BACnet.Protocol.ApplicationTags.Encoding values of type BOOLEAN, INTEGER, Unsigned, Enumerated or REAL. A singleton list of those encodings is also accepted. Booleans become zero or one, and enumerations use their unsigned numeric value. Convert application-specific enumeration atoms to their BACnet numeric encoding in the host adapter, for example with BACnet.Protocol.ObjectsUtility.cast_value_to_property/4. DOUBLE, NULL, constructed values, multi-value lists and other unsupported values are missed samples. Numeric conversion and aggregate results use single-precision REAL through BACnet.Protocol.ApplicationTags, including its configured float-decoding rounding.

    REAL special values :inf, :infn and :NaN remain valid samples. Opposite infinities give a NaN mean, and any infinite sample gives NaN variance. A NaN sample propagates to all four statistics while retained, with unspecified extrema timestamps. If there are no valid samples, minimum is :inf, maximum is :infn, mean and variance are :NaN, and optional timestamps are unspecified. Check counts and special values before using the statistics in application logic.

    Configuration and reset writes

    Supply window_interval in seconds. The default window_samples is 15. Local execution requires both values to be positive and the resulting period to be at least one millisecond. This implementation's minimum window interval is one second. These timing limits reflect its millisecond clock resolution, rather than a BACnet-wide minimum. Sample counts above 15 are supported when their period satisfies that limit.

    Initialization and accepted writes to any of these properties clear the entire buffer:

    • attempted_samples - only zero may be written by a BACnet client.
    • object_property_reference - selecting the same source also resets the window.
    • window_interval and window_samples - same-value writes also reset the window.

    Resetting publishes zero counts, empty statistics and unspecified optional timestamps. The first sample is due one new period after reset, without an immediate source read. There is no independent count-only mode, standardized out_of_service switch or priority array. Calculated properties are read-only to BACnet clients. Low-level update_property/3 updates storage without executing or clearing the runtime buffer - client writes need lifecycle preparation and execution, as described below.

    Lifecycle integration

    The object execution host owns storage, operation ordering, clocks, callback routing and timers. The module owns sampling, the rolling window and the calculations. The host needs to:

    1. Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2, an initialization trigger and fresh state. Retain the complete result before serving live statistics.
    2. Supply a bounded read callback in BACnet.Protocol.ObjectExecution.Context. It needs to obtain the identified property's current value, including its array index, and refresh any dependent computed object before returning its value. Detect cyclic reads rather than synchronously entering an already executing owner.
    3. Retain each result's object, opaque state and replacement wakeup together, and deliver due timers with fresh clocks and the retained state. See the timer arming, replacement and stale-delivery examples in BACnet.Protocol.ObjectExecution.Lifecycle.
    4. Prepare client writes with BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3. Commit the returned candidate, then execute the same write trigger before processing the next external operation. This is required even when the written value is unchanged.
    5. Use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2 before reading statistics. A due read can acquire one sample and returns an updated lifecycle result to retain first.

    Local references are supported. An explicit reference to the context's device_identifier normalizes to a local reference. Other device-qualified references are passed to the read callback unchanged, including when the local identity is nil. Remote acquisition is supported through that callback - the host needs to resolve routing and access and return the value or an operational error. A remote Averaging snapshot itself remains passive.

    Timing, failures and restart

    Sampling uses VM-monotonic milliseconds. Deadlines are rounded up from the absolute rational schedule, so fractional periods do not accumulate rounding drift. Wall-clock corrections affect acquisition timestamps, without moving the monotonic sampling origin. Early or repeated calls preserve the pending request and do not reacquire the same slot.

    If delivery is late, expired earlier slots become missed attempts and one instantaneous sample is acquired for the latest due slot at the supplied current wall time. Execution does not issue repeated current reads as historical samples. Work and retained storage are bounded by the configured sample count even after a long pause. The next deadline retains the original cadence. Slow callbacks can make later slots late - the host needs to bound callback waits and resample clocks for subsequent steps.

    Preflight rejects malformed configuration, incompatible runtime state and a missing read callback before I/O. Lifecycle execution does not execute intrinsic reporting. A failed read or unsupported value returns {:ok, result}, with a missed attempt and error details in opaque runtime state, so the host can retain progress and continue sampling. A successful acquisition clears the latest error. Averaging has no Reliability property or standardized intrinsic algorithm. Callback exceptions and malformed callback results remain programming errors.

    Keep the sample buffer as well as the object while the instance is running - aggregates alone cannot reconstruct a sliding window. After a VM restart, initialize with fresh state and clocks. This discards samples, resets statistics and schedules the first new acquisition. Do not restore old VM-monotonic timestamps. A separate BACnet.Protocol.ObjectTypes.EventEnrollment can monitor a statistic for algorithmic reporting when that integration is implemented.

    Examples

    Creating an Averaging object for a one-hour window:

    iex> {:ok, average} = BACnet.Protocol.ObjectTypes.Averaging.create(300, "AvgTemp", %{window_interval: 3600})
iex> {average.object_name, average.window_samples}
{"AvgTemp", 15}

    Initializing and driving one sample with explicit clocks:

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> alias BACnet.Protocol.ObjectTypes.Averaging
iex> {:ok, object} = Averaging.create(301, "One-minute statistics", %{window_interval: 60})
iex> context = Context.new(:initialization, now: ~U[2026-11-09 08:00:00Z],
...>   monotonic_time: 0, read_property: fn _reference -> {:ok, 21.5} end)
iex> {:ok, stored} = Lifecycle.execute(object, context)
iex> {stored.object.valid_samples, stored.next_execution.monotonic_time}
{0, 4000}
iex> timer_context = %{context | trigger: :timer, state: stored.state,
...>   now: ~U[2026-11-09 08:00:04Z], monotonic_time: 4000}
iex> {:ok, stored} = Lifecycle.execute(stored.object, timer_context)
iex> {stored.object.valid_samples, stored.object.average_value}
{1, 21.5}

    This snippet represents retention by rebinding stored. A complete finite walkthrough of rolling windows, failed reads, resets and remote references is available in examples/objects_lifecycle/averaging_lifecycle.exs in the repository.

    For many observers sharing a source, a host may share acquisition or cache work when it can still supply the required sample at each object's due time. It needs to preserve each instance's independent window and avoid presenting a stale cached value as a successful fresh acquisition.

    @type common_object_opts() ::

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
