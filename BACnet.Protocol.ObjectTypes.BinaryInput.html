    BACnet.Protocol.ObjectTypes.BinaryInput (bacstack v0.1.0-dev.2)

    View Source

    A Binary Input represents a two-state sensor or contact, such as a door switch or a pump run signal. Its Boolean present_value is the logical reading after applying polarity. Use device_type to describe the connected hardware.

    The object supports out-of-service simulation and reliability indication. Its core lifecycle applies polarity, maintains optional logical history and accumulates active seconds. It also evaluates intrinsic alarms when selected at creation.

    Object Description (ASHRAE 135)

    The Binary Input object type defines a standardized object whose properties represent the externally visible characteristics of a binary input. A "binary input" is a physical device or hardware input that can be in only one of two distinct states.

    Binary Input objects that support intrinsic reporting shall apply the CHANGE_OF_STATE event algorithm.

    Behaviour and Operation

    Binary Input is the standard representation of a dry contact, run indication or limit switch. The host's sensor adapter reads the hardware. set_input/2 builds a candidate from its raw Boolean sample: NORMAL preserves the sample and REVERSE inverts it. active_text and inactive_text describe those logical states for human consumption. The wire representation remains enumerated INACTIVE/ACTIVE.

    Lifecycle and host contract

    The object execution host is the integrating application or higher-level stack that retains objects and runtime state, serializes operations and supplies clocks, sensor samples and requested wakeups. This module starts no process, reads no clock and invokes no hardware or property callbacks.

    Initialize with BACnet.Protocol.ObjectExecution.Lifecycle.execute/2, :initialization and a fresh BACnet.Protocol.ObjectExecution.Context. Retain the full returned result. For a physical sample, call set_input/2, then BACnet.Protocol.ObjectExecution.Lifecycle.prepare_write/3 with {:application_write, :present_value, nil, nil}. Commit the prepared candidate and execute with the same clocks and previous runtime state before exposing another operation. Deliver each accepted sample, including same-value samples, and retain every result's object, state and replacement wakeup. Property setters alone do not run history accounting.

    set_input/2 retains the raw sample in _metadata.physical_input, not in a BACnet property. The existing physical_input creation option supplies an initial raw Boolean sample; nil means unknown. A nil sample through set_input/2 marks the physical input unknown without inventing a new logical value. The host needs to supply physical reliability separately - absence of a sample does not infer a particular hardware fault here.

    Polarity and Interface_Value

    While in service, a polarity edit recomputes present_value from the retained sample. With no known sample, it inverts the previous logical value when polarity changes, without asserting knowledge of the physical input. While out of service, polarity does not alter the simulated present_value. Returning to service uses the latest retained sample when one is known. The host needs to supply a fresh sample/status if retained observations are insufficient for its application.

    The optional interface_value reports the physical input mapped through current polarity, even during out-of-service simulation. It is :undefined when the raw input is unknown, which encodes as BACnet NULL. A nil property value means the optional property is absent. It is read-only to BACnet clients and is maintained as a related property of input, polarity and out-of-service updates. set_input/2 does not create the optional property - select it explicitly with interface_value: :undefined at creation, or pass :undefined to add_property/3.

    Out of service, simulation and reliability

    BACnet present_value writes use {:property_write, property, index, priority} and are rejected with {:error, :write_access_denied} while in service. Out of service, BACnet writes can simulate logical values. Write priority is ignored for this non-commandable object. The host still needs to enforce service permissions and indices.

    Physical samples may continue while out of service: set_input/2 retains them and updates a selected Interface_Value, but preserves the simulated Present_Value. A local application candidate that changes the simulated value returns {:error, :out_of_service}. Explicit Reliability writes from either application or BACnet origin can simulate conditions while out of service, including same-value writes. The host needs to stop forwarding automatic hardware Reliability reports while decoupled. Origin alone does not distinguish an automatic report from intentional simulation. Logical history and active-time accounting continue to follow simulated Present_Value.

    reliability_evaluation_inhibit masks automatic reliability with :no_fault_detected, except for an explicitly supplied out-of-service simulation. The retained physical reliability becomes effective when inhibition ends or when returning to service, if known and evaluation is not inhibited. Physical reports received while inhibited are retained for that later evaluation. With no retained physical reliability, the current supplied value remains until a fresh report. Initialization treats a supplied out-of-service reliability value as initial simulation. Existing property mechanics keep the corresponding fault and OOS status flags synchronized. The host owns any local overridden indication and its hardware diagnosis.

    Logical history and active seconds

    The optional change_of_state_time, change_of_state_count and time_of_state_count_reset form one group. Every actual effective Present_Value transition increments the existing non-negative integer count and stamps device-local wall time. The count has no imposed wrap limit. Repeated identical samples do not count, but an in-service polarity change that changes Present_Value does.

    elapsed_active_time and time_of_active_time_reset form another optional group. Monotonic ACTIVE milliseconds accumulate into whole seconds, retaining fractions across inactive periods. The unsigned 32-bit seconds total wraps modulo 2^32 without a reset stamp. Zero writes to either total stamp its reset time, including repeated zero writes. Nonzero writes leave reset timestamps unchanged. Reset timestamps are writable and do not themselves clear totals. Replacing the active-time total clears its fractional part.

    Service the returned monotonic second-boundary wakeups while ACTIVE. Before computed reads, use BACnet.Protocol.ObjectExecution.Lifecycle.prepare_read/2, retain its result and call the getter. Wall-clock corrections affect timestamps, not elapsed durations. The host needs to deliver input transitions promptly - polling cannot recover transitions that were never supplied to the object.

    A complete physical-sample operation with supplied clocks:

    iex> alias BACnet.Protocol.ObjectExecution.{Context, Lifecycle}
iex> {:ok, object} = BACnet.Protocol.ObjectTypes.BinaryInput.create(7, "Contact", %{change_of_state_count: 0, interface_value: :undefined})
iex> start = Context.new(:initialization, now: ~U[2026-11-08 10:00:00Z], monotonic_time: 0)
iex> {:ok, stored} = Lifecycle.execute(object, start)
iex> sample = Context.new({:application_write, :present_value, nil, nil}, now: ~U[2026-11-08 10:00:01Z], monotonic_time: 1000, state: stored.state)
iex> {:ok, candidate} = BACnet.Protocol.ObjectTypes.BinaryInput.set_input(stored.object, true)
iex> {:ok, prepared} = Lifecycle.prepare_write(stored.object, candidate, sample)
iex> {:ok, stored} = Lifecycle.execute(prepared, sample)
iex> {stored.object.present_value, stored.object.interface_value, stored.object.change_of_state_count}
{true, true, 1}

    Initialization and capability boundaries

    Initialization establishes a baseline from the current sample/value without fabricating a historical transition. Existing totals and reset timestamps are retained. Newly added history groups start accounting at that operation. After a VM restart, initialize with fresh clocks and runtime state. Invalid/cross-instance state or backwards monotonic time returns {:error, :invalid_execution_state} without a replacement result. Rejected writes leave the original object, state and wakeup unchanged and do not set a hardware fault.

    Intrinsic reporting

    Create a local Binary Input with intrinsic_reporting: true to evaluate CHANGE_OF_STATE against the logical present_value and alarm_value. Simulated values participate while out of service. Alarm and normal delays use monotonic time. The next wakeup covers the earliest reporting or history deadline. A condition that clears before its delay expires starts a fresh delay when it recurs.

    Reliability faults take precedence over the alarm condition. Fault recovery records a return to normal and requests an immediate reevaluation if the alarm condition still applies. event_algorithm_inhibit clears offnormal alarms and leaves fault detection active. A linked inhibit property is read through the host and keeps its last value if the read fails. The host needs to reevaluate when the linked property changes. Disabling event_detection_enable resets the reporting properties and cancels pending event delays.

    The host needs to call transition/1 for each committed result, including intermediate results before immediate continuations. For an enabled transition with a routing plan, use the plan's recipients and priority to deliver BACnet.Protocol.Services.ConfirmedEventNotification or BACnet.Protocol.Services.UnconfirmedEventNotification. If the class lookup fails, the object still records the transition and timestamp. For an alarm acknowledgment, use acknowledge/3 to match the timestamp and update the acknowledgment bit. The host handles the acknowledgment service and delivery. Remote snapshots remain passive and request no wakeup.

    Examples

    Creating a Binary Input with state texts:

    iex> {:ok, bi} = BACnet.Protocol.ObjectTypes.BinaryInput.create(5, "Door Contact", %{active_text: "Open", inactive_text: "Closed"}); bi.active_text
"Open"

    Selecting an initial physical sample and the intrinsic property representation:

    iex> {:ok, bi} = BACnet.Protocol.ObjectTypes.BinaryInput.create(6, "RunStat", %{}, intrinsic_reporting: true, physical_input: true); is_boolean(bi.present_value)
true

    Common object options for creation - all are optional.

    • allow_numeric_constants - Constants are atoms and thus unknown constants or vendor extensions are integers and thus are rejected. Enabling this option will allow integers (non_neg_integer()) for properties with a Constants.type() spec.
    • allow_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties (numeric identifiers usually means we dont know them) are accepted and put into a separate map. This does mean we can not validate or write them. Types of the values can be anything at this point. While you can read unknown properties with atom or integer as property identifier, you can only remove numeric unknown property identifiers from an object. Property identifiers of type atom are only accepted, if it is a remote object (object implementation is only enforced if it is a local object). Numeric property identifiers are accepted regardless of remote object or not. For remote objects, this means you have to write "raw values" (usually BACnet.Protocol.ApplicationTags.Encoding structs).
    • ignore_unknown_properties - Properties that are unknown to the object implementation are usually rejected. With this option, unknown properties get ignored, as if they were not specified.
    • revision - The BACnet protocol revision used for required properties and annotation conditions. Accepts a non-negative protocol revision number (for example, 19) or a name from BACnet.Protocol.Constants.protocol_revision/0. Optional properties remain available unless an annotation prohibits them. Default required annotations use ASHRAE 135-2012 (revision 14), or the addendum/revision that introduced a later object type.
    • skip_property_validation_remote_object - Skips property validation for remote objects. Sometimes it is possible that the value is invalid as per BACnet specification (i.e. value 0 for a multistate object), but you still want those to be represented. Value true neither type nor value are validated. Value :value means the type is still validated and only the value validator is not run (if present). The property's validator_fun will also be skipped.
